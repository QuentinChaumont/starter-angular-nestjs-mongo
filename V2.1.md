# Starter Nx Angular + NestJS + Mongo — V2.1

## Objectif

La V2 a livré la couche frontend (design, auth, dashboard, feedback,
consent) et l'auth avancée backend (refresh + OIDC), plus l'inscription
self-service (phase 9).

La **V2.1** ne change pas l'architecture : même principe de briques opt-in
installées par des generators Nx locaux. Elle comble les manques qui
empêchent aujourd'hui de démarrer un vrai projet sur le starter :

1. **durcir l'auth** — `POST /api/users` encore ouvert, pas de garde
   anti-brute-force sur `login` / `register` ;
2. **e-mail transactionnel** — brique `mailer` à transport *console* par
   défaut (zéro dépendance externe), pré-requis du reset de mot de passe ;
3. **mot de passe oublié / réinitialisation** (+ vérification d'e-mail
   optionnelle) ;
4. **profil utilisateur** — `GET`/`PATCH /api/users/me`, page
   `/app/profile`, changement de mot de passe ;
5. **console d'administration** — la route `/app/admin` est un placeholder,
   la remplacer par une vraie liste paginée + gestion des rôles ;
6. **generator de module métier lazy-loaded** — la brique qui rend le
   starter productif (déjà identifiée comme V2.1 dans la conversation) ;
7. **CI + conteneurisation** — rendre le starter livrable ;
8. **tests E2E navigateur** (Playwright) — on n'a que de l'unit/integration.

Le starter doit rester **modulaire** : un projet qui n'a besoin ni de
`mailer`, ni de reset, ni d'admin UI doit pouvoir garder le socle V1 + les
briques V2 intactes.

---

## Priorités

| Priorité | Steps | Raison |
| --- | --- | --- |
| **P1** | 31, 32, 33, 36, 37 | Sécurité + productivité + livrabilité |
| **P2** | 34, 35, 38 | Confort / complétude |

`32` est un pré-requis dur de `33`. `36` est indépendant. `34` et `35`
dépendent du brick auth V2 (déjà là).

---

## À trancher avant implémentation

Ces points ne sont **pas** encore décidés — les arbitrer au lancement de
chaque step, pas pendant l'implémentation.

1. **`mailer` — transport par défaut.** Console (log structuré) vs. fichier
   `.eml` dans `tmp/` vs. Ethereal/Nodemailer test account. Reco : console
   + interface `MailTransport` pluggable (SMTP fourni en option, activé par
   `SMTP_URL`).
2. **Vérification d'e-mail — bloquante ou non.** À l'inscription : compte
   utilisable tout de suite avec bannière « vérifiez votre e-mail » (soft),
   ou login refusé tant que non vérifié (hard). Reco : soft, avec un flag
   `AUTH_REQUIRE_VERIFIED_EMAIL=false` par défaut.
3. **Reset — durée de vie et usage unique du token.** Reco : token opaque
   hashé (SHA-256, comme les refresh tokens), TTL 1 h, à usage unique,
   invalidé par un changement de mot de passe.
4. **`frontend-feature` — nom & profondeur.** `frontend-feature <name>`
   (page liste + détail + service) vs. `entity <name> --crud --frontend`
   (génère backend + frontend alignés sur le contrat partagé). Reco :
   les deux — `entity --frontend` réutilise le generator `frontend-feature`.
5. **Admin UI — périmètre.** Liste + rôles seulement, ou aussi
   création/désactivation/suppression. Reco : liste paginée + toggle rôles
   + désactivation ; pas de suppression (soft-delete plus tard).
6. **CI — plateforme.** GitHub Actions supposé (`gh` déjà utilisé). À
   confirmer si GitLab CI / autre.

---

## Principes (repris de V1 / V2)

- Chaque step : analyser l'existant, implémenter **uniquement** son
  périmètre, `nx run-many -t lint test build typecheck` vert, remplir le
  « Résumé d'implémentation » + le coût tokens en fin de step.
- Briques opt-in via generators `tools/starter-plugin`, idempotents, jamais
  imposées au runtime.
- Modules **infra** eager ; modules **métier** lazy-loaded (cf. step 36).
- Config uniquement via `AppConfigService` — jamais `process.env` hors
  `libs/backend/core/config`. Toute nouvelle variable ajoutée à
  `ENVIRONMENT_VARIABLE_NAMES`.
- Contrats front/back dans `libs/shared/contracts`.
- Pas de Redis, pas de Sentry, pas d'observabilité (inchangé depuis V2).

# STEP 31 — Durcissement de l'authentification

## Objectif

Fermer les deux trous laissés ouverts par les steps V1/V2 :
`POST /api/users` non gardé, et aucune limite spécifique sur les routes
sensibles `login` / `register` (le throttler global à 100 req/min ne
protège pas d'un bourrage ciblé).

## Emplacement

- `libs/backend/features/user/src/lib/user.controller.ts` — gardes.
- `libs/backend/auth/src/lib/` — guard/décorateur de rate-limit dédié.
- `libs/backend/core/src/lib/config/` — nouvelles variables.

## Dépendances

Briques `auth` + `security` (throttler) installées.

## Fonctionnalités

- `POST /api/users`, `PATCH /api/users/:id`, `DELETE /api/users/:id` :
  `@UseGuards(JwtAuthGuard, RolesGuard)` + `@Roles('admin')`.
  `GET /api/users` : idem (liste réservée admin). Le starter garde un
  moyen de créer le **premier** admin : commande `nx g
  @org/starter-plugin:seed-admin` (ou script `pnpm seed:admin`) qui insère
  un compte `admin` en base à partir de `SEED_ADMIN_EMAIL` /
  `SEED_ADMIN_PASSWORD`.
- Rate-limit dédié : `@Throttle` (ou guard maison) sur `POST /auth/login`
  et `POST /auth/register` — fenêtre + plafond propres, configurables :
  `AUTH_RATE_LIMIT_TTL_SECONDS` (défaut 60), `AUTH_RATE_LIMIT_LIMIT`
  (défaut 10). Réponse `429` au format `ApiError`.
- (Optionnel, à trancher) verrouillage temporaire du compte après N échecs
  consécutifs de `login` — compteur en base sur le user, remis à zéro au
  succès.

## Generator

Pas de nouveau brick. La garde admin sur `user.controller.ts` est appliquée
par le generator `auth` (il « possède » déjà la relation user⇄auth) : quand
`auth` est installé, le controller user passe en admin-only. Ajouter un
generator `seed-admin` (écrit le script + la doc).

## Config

`SEED_ADMIN_EMAIL`, `SEED_ADMIN_PASSWORD`, `AUTH_RATE_LIMIT_TTL_SECONDS`,
`AUTH_RATE_LIMIT_LIMIT` — toutes optionnelles, ajoutées à
`ENVIRONMENT_VARIABLE_NAMES` + `.env.example` + tableau README.

## Contraintes

- Sans la brique `auth`, `POST /api/users` reste ouvert (le starter V1 nu
  n'a pas de notion de rôle) — le durcissement est une conséquence de
  l'install `auth`, documentée.
- Le seed est **idempotent** (ne recrée pas l'admin s'il existe).

## Critères d'acceptation

- `POST /api/users` sans token → 401 ; avec un token non-admin → 403 ;
  avec un token admin → 201.
- 11 `POST /auth/login` en < 60 s depuis la même IP → le 11ᵉ renvoie 429.
- `pnpm seed:admin` crée un compte admin connectable ; relancé → no-op.
- `nx run-many -t lint test build typecheck` vert.

## Résumé d'implémentation

**Fait.** `nx run-many -t lint test build typecheck` → 16/16 projets OK.
Vérifié en live : `POST /users` → 401 sans token, 403 non-admin, 201 admin ;
`GET /health/live` + `GET /auth/me` inchangés ; 11ᵉ `POST /auth/login` en
< 60 s → 429 ; `seed:admin` crée puis no-op.

**Réorganisation authz (pré-requis).** `AuthenticatedUser`, `@Roles` /
`ROLES_KEY`, `@CurrentUser`, `RolesGuard`, `JwtAuthGuard` + nouveau
`OptionalJwtAuthGuard` déplacés de `libs/backend/auth` vers
`libs/backend/core/src/lib/auth/` (socle, toujours présent) → le feature
`user` peut décorer ses routes sans dépendre du brick auth (pas de cycle
`user → auth → user`). `@org/backend-auth` les ré-exporte pour compat.
`backend-core` gagne `@nestjs/passport` + `passport`.

**Enforcement.** `AuthModule` lie deux `APP_GUARD` globaux :
`OptionalJwtAuthGuard` (attache `request.user` si bearer valide, no-op
sinon) puis `RolesGuard` (n'agit que sur les routes portant `@Roles(...)` ;
401 si non authentifié, 403 si rôle manquant). Sans le brick auth : aucun
guard lié → `@Roles` inerte, les routes restent ouvertes (socle nu).

**`user.controller.ts`.** `@Roles('admin')` au niveau classe +
`@ApiBearerAuth()`. `POST/GET/PATCH/DELETE /users` deviennent admin-only
dès que le brick auth est là. `auth.e2e.spec.ts` seed désormais via
`UserService` ; nouveau bloc « admin-only user administration » (401/403/201).

**Rate-limit dédié.** `AuthThrottlerGuard` (fenêtre glissante en mémoire,
clé `method+path+ip`) sur `POST /auth/login` + `POST /auth/register`.
Config `AUTH_RATE_LIMIT_LIMIT` (défaut 10) / `AUTH_RATE_LIMIT_TTL_SECONDS`
(défaut 60), optionnelles, via `config.security.authRateLimit`. Nouvelle
erreur socle `TooManyRequestsError` (429, format `ApiError`).

**Seed admin.** `apps/backend/src/seed-admin.ts` (idempotent : crée ou
promeut) + 2ᵉ entrée webpack (`additionalEntryPoints`) → `dist/seed-admin.js`,
cible `nx run @org/backend:seed-admin` (`dependsOn: build`), script racine
`pnpm seed:admin`. Config `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD`.

**Generator `auth`.** `wireSeedAdmin()` ajouté (copie le script, patche
`webpack.config.js`, ajoute la cible + le script racine), idempotent.
Le durcissement de `user.controller.ts` voyage dans le brick pristine
(via `entity`), pas de patch generator.

**Correctif connexe.** `apps/frontend` build production :
`optimization.fonts.inline: false` — l'inline des Google Fonts au build
(step précédent) échoue hors-ligne / en CI ; chargées au runtime, à
self-héberger en prod (déjà noté dans DESIGN.md).

**Coût tokens — step 31 :** ~230k.

# STEP 32 — Brique `mailer` (e-mail transactionnel)

## Objectif

Fournir un envoi d'e-mail **sans dépendance externe par défaut**, pré-requis
du reset de mot de passe (step 33) et de la vérification d'e-mail. Le
starter doit pouvoir tourner en local sans SMTP.

## Emplacement

- `libs/backend/mailer/` (nouveau lib, `type:util`, scope `backend`).
- `libs/backend/mailer/src/lib/` : `mail.types.ts` (`MailMessage`,
  `MailTransport`), `console.transport.ts` (défaut), `smtp.transport.ts`
  (optionnel), `mailer.service.ts`, `mailer.module.ts`,
  `templates/` (rendu simple, pas de moteur lourd — littéraux + interpolation
  ou `mjml` en option).

## Dépendances

Aucune obligatoire. `nodemailer` seulement si `SMTP_URL` est configuré
(dependency optionnelle du brick).

## Fonctionnalités

- `MailerService.send(message: MailMessage)` — `{ to, subject, text, html? }`.
- `MailTransport` : interface à une méthode. Deux implémentations livrées :
  - **console** (défaut) — log structuré via `AppLogger` (`to`, `subject`,
    corps tronqué) + écriture optionnelle d'un `.eml` dans `tmp/mail/`.
  - **SMTP** — `nodemailer` sur `SMTP_URL`, activée automatiquement si la
    variable est présente.
- `MAIL_FROM` (défaut `no-reply@localhost`), `MAIL_PREVIEW_DIR` (défaut
  `tmp/mail`).
- Templates typés : `renderPasswordReset({ url, expiresInMinutes })`,
  `renderEmailVerification({ url })`, `renderWelcome({ firstName })`.

## Generator

`nx g @org/starter-plugin:mailer` — copie le lib, enregistre le path
`@org/backend-mailer`, ajoute `MailerModule` aux imports de l'app backend,
ajoute les variables à `.env.example`. Idempotent.

## Config

`SMTP_URL` (optionnel), `MAIL_FROM`, `MAIL_PREVIEW_DIR` — dans
`ENVIRONMENT_VARIABLE_NAMES`, `.env.example`, README.

## Contraintes

- Zéro appel réseau tant que `SMTP_URL` n'est pas défini.
- Le rendu des templates ne doit pas tirer une grosse lib par défaut.
- `MailerService` injectable partout ; testable avec un transport en
  mémoire (`InMemoryMailTransport` exporté depuis `@org/backend-testing`).

## Critères d'acceptation

- Sans `SMTP_URL` : `send()` logge et (option) dépose un `.eml`, ne lève
  pas.
- Avec `SMTP_URL` pointant sur un serveur de test (Mailpit/Ethereal) :
  l'e-mail arrive.
- `nx run-many -t lint test build typecheck` vert.

## Résumé d'implémentation

**Fait.** `nx run-many -t lint test build typecheck` → 17/17 projets OK
(nouveau projet `backend-mailer`). Vérifié en intégration : `MailerModule`
booté via `Test.createTestingModule`, `MailerService.send()` → transport
console → `.eml` déposé, aucune exception.

**Arbitrages retenus** (point 1 « à trancher ») : transport **console** par
défaut (log structuré `AppLogger` + `.eml` dans `MAIL_PREVIEW_DIR`), zéro
réseau / zéro dépendance externe. Interface `MailTransport` pluggable ;
`SmtpMailTransport` sélectionné automatiquement dès que `SMTP_URL` est
présent. `nodemailer` reste une **`optionalDependency`** du brick (non
installée par le generator) : chargée en `import()` dynamique
(`webpackIgnore`, spécifier non-littéral pour ne pas la résoudre au build),
message actionnable au 1ᵉ `send()` si absente.

**Nouveau lib `libs/backend/mailer`** (`@org/backend-mailer`, `scope:backend`
`type:util`) : `mail.types.ts` (`MailMessage`, `OutgoingMail`,
`MailTransport`, token `MAIL_TRANSPORT`), `console.transport.ts` (rendu
`.eml` RFC-822 multipart, échec d'écriture *warn*é et avalé — ne lève
jamais), `smtp.transport.ts`, `mailer.service.ts` (injecte le transport +
`AppConfigService`, tamponne le `From`), `mailer.module.ts` (`@Global`,
factory provider qui choisit le transport), `in-memory.transport.ts`
(`InMemoryMailTransport` — exporté depuis `@org/backend-mailer` et **pas**
`@org/backend-testing`, pour ne pas coupler la lib testing à un brick
optionnel), `templates/render.ts` (`renderPasswordReset`,
`renderEmailVerification`, `renderWelcome` → `{ subject, text, html }` ;
littéraux + `escapeHtml`, aucun moteur de template). Specs : templates,
service, console transport, module (intégration).

**Config (socle).** `SMTP_URL`, `MAIL_FROM` (défaut `no-reply@localhost`),
`MAIL_PREVIEW_DIR` (défaut `tmp/mail`) ajoutées à `EnvironmentVariables` +
`ENVIRONMENT_VARIABLE_NAMES` + `validate-env.ts` (optionnelles) +
`AppConfigService.mailer` + specs `validate-env` / `app-config.service`.
Suivi du pattern V2.1 : la config des bricks vit dans `backend-core`, pas
patchée par le generator.

**Generator `mailer`.** `tools/starter-plugin/src/generators/mailer/` :
`ensureLibCopied` + `addDependenciesToPackageJson`
(`readPackageDependencies` — `@nestjs/common` seul, jamais `nodemailer`) +
`ensureNamedImport`/`ensureArrayItem` `MailerModule` dans `app.module.ts`.
Idempotent. Enregistré dans `generators.json`. `generator.spec.ts` (4 cas).

**Câblage de référence.** `MailerModule` ajouté aux `imports` de
`apps/backend/src/app/app.module.ts` + `@org/backend-mailer` dans
`apps/backend/package.json` ; `nx sync` a mis à jour les project references
(`apps/backend/tsconfig.app.json`, `tsconfig.json`). Section « Mailer brick »
dans `.env.example` ; ligne generator + 3 lignes de tableau env dans
`README.md`.

# STEP 33 — Mot de passe oublié / réinitialisation + vérification d'e-mail

## Objectif

Parcours complet « j'ai oublié mon mot de passe », et vérification d'e-mail
à l'inscription (non bloquante par défaut).

## Emplacement

- `libs/backend/auth/src/lib/reset/` : `reset-token.schema.ts`
  (collection `password_reset_tokens`, TTL index), `reset-token.service.ts`
  (émission/consommation, hash SHA-256, usage unique), `reset.controller.ts`.
- `libs/backend/auth/src/lib/verification/` : idem pour la vérification
  d'e-mail (`email_verification_tokens`).
- `libs/frontend/auth/src/lib/reset/` : `forgot-password-page.ts`
  (`/forgot-password`), `reset-password-page.ts` (`/reset-password?token=…`).
- `libs/shared/contracts/src/lib/auth.ts` : `ForgotPasswordRequest`,
  `ResetPasswordRequest`.

## Dépendances

Brique `mailer` (step 32) installée — le generator `reset` la refuse sinon,
avec un message explicite.

## Fonctionnalités

Backend :

- `POST /api/auth/forgot-password` `{ email }` → **toujours 202** (pas
  d'énumération de comptes). Si le compte existe : émet un token, envoie
  `renderPasswordReset`.
- `POST /api/auth/reset-password` `{ token, password }` → vérifie le token
  (non expiré, non consommé), change le mot de passe, **révoque toutes les
  sessions** de l'utilisateur (`refreshTokens.revokeAllForUser`), consomme
  le token. `400` si token invalide.
- Inscription (step V2 phase 9) : après `register`, émet un token de
  vérification et envoie `renderEmailVerification`.
- `POST /api/auth/verify-email` `{ token }` → marque `emailVerifiedAt` sur
  le user. `POST /api/auth/resend-verification` (authentifié) → renvoie.
- `user.schema.ts` : champ `emailVerifiedAt?: Date`.
- Flag `AUTH_REQUIRE_VERIFIED_EMAIL` (défaut `false`) : si `true`, `login`
  refuse (`403 EMAIL_NOT_VERIFIED`) tant que non vérifié.

Frontend :

- `LoginPage` : lien « Forgot password? ».
- `ForgotPasswordPage` : champ e-mail → message neutre de confirmation.
- `ResetPasswordPage` : lit `token` en query, formulaire nouveau mot de
  passe → succès → redirige `/login`.
- Bannière « Vérifiez votre e-mail » dans le shell si
  `user.emailVerifiedAt` est absent (bouton « renvoyer »).

## Generator

`nx g @org/starter-plugin:auth-reset` (ou option `--reset` du generator
`auth`). Copie les fichiers backend + frontend, câble les routes
`/forgot-password` + `/reset-password`, ajoute les variables.

## Config

`AUTH_REQUIRE_VERIFIED_EMAIL`, `RESET_TOKEN_TTL_MINUTES` (défaut 60),
`VERIFICATION_TOKEN_TTL_HOURS` (défaut 24).

## Contraintes

- `forgot-password` : réponse et timing **constants** que le compte existe
  ou non.
- Tokens : opaques, hashés en base, usage unique, jamais logués en clair.
- Un reset réussi invalide toutes les sessions actives.

## Critères d'acceptation

- `forgot-password` sur un e-mail inconnu → 202, aucun e-mail, même délai
  qu'un e-mail connu.
- Reset avec un token expiré / déjà utilisé → 400.
- Après reset, les anciens refresh tokens sont refusés (401).
- E2E : inscription → e-mail de vérif en console → `verify-email` → bannière
  disparaît.
- `nx run-many -t lint test build typecheck` vert.

## Résumé d'implémentation

**Fait.** `nx run-many -t lint test build typecheck` → 18/18 projets OK
(nouveau projet `backend-auth-reset`). E2E (vrai Mongo + `InMemoryMailTransport`) :
`forgot-password` inconnu → 202 sans e-mail ; connu → 202 + lien émis ;
token invalide → 400 ; reset → 204, sessions révoquées (ancien refresh → 401),
token à usage unique, ancien mot de passe KO / nouveau OK ; inscription →
e-mail de vérification capturé ; `verify-email` → `emailVerifiedAt` posé,
visible sur `/auth/me`.

**Arbitrages retenus.** (2) Vérification **soft** : `AUTH_REQUIRE_VERIFIED_EMAIL`
défaut `false`, compte utilisable + bannière. (3) Tokens opaques 32 o hashés
SHA-256, usage unique, TTL (`RESET_TOKEN_TTL_MINUTES` 60 /
`VERIFICATION_TOKEN_TTL_HOURS` 24), balayés par index TTL Mongo ; un reset
invalide aussi les autres liens de reset du user. (generator) Nouveau
generator **`auth-reset`** (refuse sans `auth` ni `mailer`), pas d'option
`--reset`.

**Brique séparée `libs/backend/auth-reset`** (`@org/backend-auth-reset`,
`scope:backend type:feature`) plutôt que des sous-dossiers de
`libs/backend/auth` (le doc) : garder le code + la dépendance
`@org/backend-mailer` hors du brick `auth` de base, pour qu'un `auth` sans
`mailer` continue de builder. Contenu : `single-use-token.ts` (base
générique `SingleUseTokenRepository` / `SingleUseTokenService` — issue /
consume / invalidateAllForUser, DRY entre reset et vérif),
`reset/` (schema `password_reset_tokens`, repo, `PasswordResetService`,
`AuthResetService` orchestrateur, `AuthResetController`, DTOs),
`verification/` (idem, `email_verification_tokens`), `auth-reset.module.ts`.
4 routes : `POST /api/auth/{forgot-password(202),reset-password(204),
verify-email(204),resend-verification(JWT,204)}`, toutes derrière
`AuthThrottlerGuard`. Liens pointant sur `CORS_ORIGINS[0]`.

**Hook inscription — `AuthEvents` (Node `EventEmitter`, zéro dépendance).**
`@nestjs/event-emitter` n'est pas servi de façon fiable par le registre
Artifactory ; un `EventEmitter` stdlib injectable (`AuthEvents`, fourni +
exporté par `AuthModule`) donne le même découplage. `AuthService.register`
émet `user.registered` ; `AuthResetService.onModuleInit` s'y abonne pour
envoyer l'e-mail de vérif (échec logué, n'interrompt pas l'inscription).
Sans `auth-reset` : aucun abonné, no-op.

**Changements brick `auth` de base** (config-gated, sûrs) :
`AuthService.login` refuse `403 EMAIL_NOT_VERIFIED` si
`config.auth.requireVerifiedEmail && !user.emailVerifiedAt` ;
`AuthService.register` émet l'événement ; `GET /auth/me` renvoie désormais
`emailVerifiedAt` (`AuthService.currentUser`, async, lit le user) →
`AuthenticatedUserDto.emailVerifiedAt?: string | null`. Nouveau
`auth.service.spec.ts` (la garde + l'émission). `auth.e2e.spec.ts` : `me`
attend `emailVerifiedAt: null`.

**Brick `user`.** `user.schema.ts` : `emailVerifiedAt?: Date` ;
`UserService.markEmailVerified(id)` (idempotent).

**Config (socle).** `AUTH_REQUIRE_VERIFIED_EMAIL` (bool, défaut false),
`RESET_TOKEN_TTL_MINUTES` (60), `VERIFICATION_TOKEN_TTL_HOURS` (24) →
`EnvironmentVariables` + `ENVIRONMENT_VARIABLE_NAMES` + `validate-env` +
`AppConfigService.auth` (le getter renvoie maintenant 4 clés) + specs.

**Frontend (`libs/frontend/auth/src/lib/reset/`, câblé par le generator si
`frontend-auth` présent).** `ResetService` (HTTP, séparé de `AuthService`),
`ForgotPasswordPage` (`/forgot-password`, message neutre),
`ResetPasswordPage` (`/reset-password?token=`, → `/login?reset=done`),
`VerifyEmailPage` (`/verify-email?token=`), `VerifyEmailBanner` (barre
montée hors router-outlet dans `app.ts`, visible si
`store.user()?.emailVerifiedAt === null`, bouton « renvoyer »). Lien
« Forgot your password? » ajouté au `login-page.ts` par le generator.
Exports en `export *` dans l'index frontend-auth (idempotents via
`ensureExportLine`).

**Generator `auth-reset`.** `ensureLibCopied` + deps + `AuthResetModule`
dans `app.module.ts` ; volet frontend conditionnel (`copySourceDirectory`
du sous-dossier `reset/`, exports, 3 routes, bannière, lien login).
`generator.spec.ts` (7 cas : refus ×2, backend, frontend, skip-frontend,
idempotence). Enregistré dans `generators.json`. Câblage de référence :
`AuthResetModule` dans l'app, `nx sync` (references), sections
`.env.example` + README.

**Dégradation sans SMTP.** `MailerService` (`OnApplicationBootstrap`) logue
un `warn` au démarrage si `SMTP_URL` absent (« configuration incomplete… »).
`AuthResetService` logue en plus, à chaque demande, le lien de reset /
vérification en clair (`warn`, contexte `AuthResetService`) tant que
`SMTP_URL` n'est pas défini — le parcours local n'est jamais bloqué. Muet
dès qu'un vrai SMTP est configuré.

**Coût tokens — step 33 :** ~460k.

# STEP 34 — Profil utilisateur

## Objectif

Exposer et éditer les données du compte connecté. Aujourd'hui `GET
/auth/me` ne renvoie que `{ id, roles }` (le miroir du JWT).

## Emplacement

- `libs/backend/features/user/src/lib/user.controller.ts` : routes `/me`.
- `libs/shared/contracts/src/lib/user.ts` : `UserProfile`,
  `UpdateProfileRequest`, `ChangePasswordRequest`.
- `libs/frontend/dashboard` ou nouveau `libs/frontend/features/profile` :
  page `/app/profile`.

## Dépendances

Brique `auth` + `frontend-auth` + `frontend-dashboard`.

## Fonctionnalités

- `GET /api/users/me` → `UserProfile` (`id, email, firstName, lastName,
  roles, emailVerifiedAt, createdAt`).
- `PATCH /api/users/me` `{ firstName?, lastName? }` — pas l'e-mail (ou
  e-mail avec re-vérification, à trancher).
- `POST /api/users/me/change-password` `{ currentPassword, newPassword }`
  → vérifie l'actuel, change, **révoque les autres sessions** (garde la
  courante).
- Frontend : `ProfilePage` (`/app/profile`), entrée dans le menu
  utilisateur, formulaires Material + `NotificationService` sur succès.
- `AuthStore` : stocker le `UserProfile` complet (pas seulement id+roles) —
  `loadMe()` tape `/users/me` au lieu de `/auth/me` quand la brique est là.

## Generator

Option `--profile` du generator `frontend-auth`, ou petit generator
`frontend-profile`. Câble la route enfant `/app/profile` + l'entrée menu.

## Contraintes

- `change-password` ne doit pas déconnecter la session courante.
- Le profil ne réintroduit pas l'e-mail dans le JWT (le token reste
  `sub` + `roles`).

## Critères d'acceptation

- `GET /users/me` sans token → 401.
- `change-password` avec un mauvais mot de passe actuel → 400, aucune
  session touchée.
- Après `change-password`, les autres refresh tokens sont révoqués, la
  session courante fonctionne toujours.
- `nx run-many -t lint test build typecheck` vert.

# STEP 35 — Console d'administration

## Objectif

Remplacer le placeholder `/app/admin` par une vraie page : lister les
utilisateurs (paginé), attribuer/retirer des rôles, désactiver un compte.

## Emplacement

- `libs/backend/features/user/` : pagination + `PATCH /users/:id/roles`,
  `PATCH /users/:id/status`.
- `libs/shared/contracts/src/lib/user.ts` : `Paginated<T>`,
  `UserSummary`, `UpdateRolesRequest`.
- `libs/frontend/features/admin-users/` (nouveau, lazy) : table Material +
  filtres + actions.

## Dépendances

Steps 31 (gardes admin) + 36 (pattern de feature lazy) recommandés.

## Fonctionnalités

- `GET /api/users?page=&pageSize=&search=` → `Paginated<UserSummary>`
  (admin only). Tri sur `createdAt`, recherche sur email/nom.
- `PATCH /api/users/:id/roles` `{ roles: string[] }` (admin only) —
  refuse qu'un admin se retire à lui-même le dernier rôle admin.
- `PATCH /api/users/:id/status` `{ active: boolean }` — un compte inactif
  ne peut plus se `login` ni `refresh` (`403 ACCOUNT_DISABLED`), sessions
  révoquées à la désactivation. Champ `disabledAt?: Date`.
- Frontend : `AdminUsersPage` sous `/app/admin` (lazy), `MatTable` +
  `MatPaginator` server-side, dialog de confirmation (`DialogService`) sur
  les actions sensibles, `roleGuard('admin')`.

## Generator

`nx g @org/starter-plugin:frontend-admin-users` (dépend de `frontend-feature`).
Câble la route lazy `/app/admin` + l'entrée `DASHBOARD_NAV` (roles: admin).

## Contraintes

- Pagination **server-side** (pas de `findAll()` complet).
- Garde-fou « dernier admin » : impossible de se verrouiller dehors.
- Pas de suppression dure (soft-delete/désactivation seulement).

## Critères d'acceptation

- `GET /users` non-admin → 403 ; admin → page 1 avec `total`.
- Retirer `admin` au dernier admin → 400.
- Désactiver un compte → ses refresh tokens sont refusés, `login` → 403.
- `nx run-many -t lint test build typecheck` vert.

# STEP 36 — Generator `frontend-feature` (module métier lazy-loaded)

## Objectif

La brique qui rend le starter productif : scaffolder un module métier
**lazy-loaded** sous le shell `/app`, aligné sur les conventions (signals,
service HTTP typé, contrat partagé, entrée de navigation).

## Emplacement

- `tools/starter-plugin/src/generators/frontend-feature/`.
- Génère `libs/frontend/features/<name>/` : `project.json` (tags
  `scope:frontend type:feature`), `src/lib/<name>.routes.ts` (routes
  **lazy** exportées), `src/lib/<name>.service.ts` (CRUD sur
  `API_BASE_URL`), `<name>-list.page.ts`, `<name>-detail.page.ts`,
  `<name>.store.ts` (signals), specs.

## Dépendances

Briques `frontend-design` + `frontend-dashboard`. Le contrat
`libs/shared/contracts/src/lib/<name>.ts` s'il existe (généré par
`entity <name>` côté backend).

## Fonctionnalités

- `nx g @org/starter-plugin:frontend-feature reports` →
  - `libs/frontend/features/reports/` complet ;
  - route lazy ajoutée aux enfants de `/app` dans `app.routes.ts` :
    `{ path: 'reports', loadChildren: () => import('@org/frontend-features-reports').then(m => m.REPORTS_ROUTES) }` ;
  - entrée `DASHBOARD_NAV` `{ label: 'Reports', icon: 'insights', route: 'reports' }` ;
  - path `@org/frontend-features-reports` dans `tsconfig.base.json`.
- Option `--crud` : pages liste (table paginée) + détail + formulaire.
- Option `--roles admin` : `canActivate: [roleGuard('admin')]` sur la route.
- `entity <name> --crud --frontend` (côté backend, generator existant
  étendu) : appelle `frontend-feature <name> --crud` après avoir généré le
  module Nest + le contrat partagé, pour des deux bouts cohérents.

## Contraintes

- **Vraiment lazy** : aucun import statique de `@org/frontend-features-*`
  dans `app.config.ts` / `app.ts` (respect de
  `@nx/enforce-module-boundaries`). La feature n'expose **pas** de
  provider chargé au bootstrap.
- Idempotent : re-run = no-op byte-for-byte (route, nav, tsconfig).
- Convention documentée : `libs/frontend/features/<x>` = métier lazy ;
  `libs/frontend/<x>` = infra eager.

## Critères d'acceptation

- Après `frontend-feature reports`, `nx build frontend` produit un **chunk
  séparé** pour `reports`.
- `nx lint frontend` ne signale aucun import statique interdit.
- Re-run du generator → `git diff` vide.
- Le `frontend-sequence.spec.ts` couvre un `frontend-feature` de bout en
  bout.
- `nx run-many -t lint test build typecheck` vert.

# STEP 37 — CI + conteneurisation

## Objectif

Rendre le starter livrable : pipeline CI et images Docker.

## Emplacement

- `.github/workflows/ci.yml`.
- `apps/backend/Dockerfile`, `apps/frontend/Dockerfile`,
  `apps/frontend/nginx.conf`.
- `docker-compose.yml` (racine) — backend + frontend + Mongo.
- `.dockerignore`.

## Fonctionnalités

CI (`ci.yml`, sur `push` + `pull_request`) :

- `pnpm install --frozen-lockfile` ;
- `nx sync:check` ;
- `nx affected -t lint test build typecheck` (base = SHA de la branche
  cible), avec `nx-set-shas` ;
- cache Nx (`actions/cache` sur `.nx/cache`) ;
- job séparé « e2e » (step 38) déclenché sur `pull_request` uniquement.

Docker :

- **backend** : multi-stage — build `nx build @org/backend` puis image
  `node:22-alpine` + `dist/` + `node_modules` de prod
  (`nx prune`/`prune-lockfile` déjà présents). Port 3000, `HEALTHCHECK` sur
  `/api/health/live`.
- **frontend** : build `nx build frontend` puis `nginx:alpine`,
  `nginx.conf` avec fallback SPA + proxy `/api` → service `backend`.
- **compose** : `mongo:7` avec volume, backend avec `.env`, frontend
  exposé sur `:8080`. `depends_on` + healthchecks.
- Generator `nx g @org/starter-plugin:docker` (écrit Dockerfiles + compose
  + `.dockerignore`) — opt-in comme le reste.

## Contraintes

- Les Dockerfiles n'installent que les deps de prod (image backend légère).
- Aucune variable secrète en dur — tout via `.env` / secrets CI.
- Le workflow doit passer sur un fork sans secrets (les jobs qui en ont
  besoin sont `if:` gardés).

## Critères d'acceptation

- `docker compose up` → `http://localhost:8080` sert le SPA, `/api/health/ready`
  répond `200`.
- `ci.yml` vert sur une PR de test.
- `nx affected` ne relance pas tout le workspace pour un changement de
  doc.

# STEP 38 — Tests E2E navigateur (Playwright)

## Objectif

Couvrir les parcours critiques dans un vrai navigateur — on n'a
aujourd'hui que de l'unit (Jest) et de l'integration (Nest + Mongo
mémoire).

## Emplacement

- `apps/frontend-e2e/` (generator `@nx/playwright`).
- `apps/frontend-e2e/src/` : `auth.spec.ts`, `consent.spec.ts`,
  `dashboard.spec.ts`.

## Fonctionnalités

- Setup : `webServer` Playwright lance `nx serve @org/backend` +
  `nx serve frontend`, Mongo via `mongodb-memory-server` ou service
  compose. Seed d'un user via l'API avant la suite.
- Parcours couverts :
  - inscription → arrivée sur `/app` → refresh (reload) → toujours
    connecté → logout → `/login` ;
  - login mauvais mot de passe → message d'erreur inline, pas de toast ;
  - bandeau consent : visible à la 1ʳᵉ visite, « Accept all » le masque,
    persiste après reload, « Manage cookies » le rouvre ;
  - page cookie policy : ouverte dans un nouvel onglet, bouton Back ;
  - route protégée sans session → redirection `/login?redirectTo=…` puis
    retour après login ;
  - `roleGuard` : `/app/admin` en user non-admin → refus.
- Intégré au job `e2e` de la CI (step 37).

## Contraintes

- Pas de dépendance à un IdP réel (OIDC testé en unit/integration
  seulement, ou via un mock provider optionnel).
- Suite < 3 min en CI (1 worker, navigateur chromium seul par défaut).
- `data-testid` sur les éléments ciblés, pas de sélecteurs fragiles.

## Critères d'acceptation

- `nx e2e frontend-e2e` vert en local et en CI.
- Un échec de parcours produit un trace Playwright exploitable
  (artefact CI).
