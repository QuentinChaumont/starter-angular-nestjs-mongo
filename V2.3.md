# Starter Nx Angular + NestJS + Mongo — V2.3

## Objectif

La V2.2 a fini de creuser l'authentification (OIDC multi-provider, liaison
de comptes, 2FA/TOTP, CRUD des rôles). La **V2.3** passe à la
**gouvernance, au contrôle des sessions et à la maturité du frontend** :

1. **Journal d'audit** — qui a fait quoi (login, changement de mot de
   passe, 2FA on/off, rôle modifié, compte désactivé, identity link/unlink),
   consultable dans la console admin.
2. **Sessions & appareils** — exposer la révocation de sessions déjà
   écrite mais jamais branchée : liste des appareils dans le profil,
   « se déconnecter partout », révocation admin.
3. **i18n (Transloco)** — `fr` / `en`, sélecteur de langue dans le shell,
   traduction des chaînes des bricks existantes, **e-mails localisés**,
   choix de langue persisté.
4. **UI kit** — factoriser les patterns recopiés (toolbar de page, bouton
   async, erreurs de formulaire, tags de statut, « il y a X min », copier,
   empty state) dans `frontend-ui`.
5. **Shell UX** — barre de progression de navigation, guard
   « modifications non enregistrées », sous-navigation à onglets pour
   `/app/admin`.

Le starter reste **modulaire** : chaque ajout est une brick opt-in (ou une
primitive de la lib toujours présente `frontend-ui`), jamais imposée.

---

## Décisions d'architecture V2.3 (déjà tranchées)

Ces choix s'appliquent à toutes les étapes. Ne pas les réinterroger
pendant l'implémentation.

### Audit — append-only, best-effort, jamais bloquant

`AuditService.record()` **n'échoue jamais** la requête d'origine (comme
l'envoi d'e-mail du brick `auth-reset`). Collection `audit_events`
append-only (pas d'update, pas de delete via l'API). Rétention par TTL
index configurable (`AUDIT_RETENTION_DAYS`, défaut 90, `0` = infini).
Émission via un `AuditEvents` (EventEmitter, même pattern que `AuthEvents`)
pour que le brick `auth` n'ait aucune dépendance dure vers `audit`.

### Sessions — pas de nouveau modèle

Les `refresh_tokens` existants **sont** la liste des sessions. On ajoute
juste `lastUsedAt` (déjà à moitié là via la rotation) et on expose une
projection. Pas de collection `sessions` séparée.

### i18n — Transloco, chargement eager, 2 langues fournies

`@jsverse/transloco`. Les fichiers `fr.json` / `en.json` sont **chargés au
démarrage** (pas de lazy scope) — le starter a peu de chaînes, le lazy
scope se rajoute par projet. Langue par défaut = `en`. Détection :
`user.locale` (si connecté) → `localStorage` → `navigator.language` → `en`.
Les e-mails prennent la langue de `user.locale` (défaut `en`).

### UI kit — dans `frontend-ui`, pas de nouvelle brick

Tous les composants du step 48 vont dans `libs/frontend/ui` (lib toujours
présente). Aucun générateur : ils arrivent avec la lib. Le step **refacte
les features existantes** pour les utiliser (admin-users, admin-roles,
profil, login, register, reset).

---

## À trancher avant implémentation

Arbitrer au lancement de chaque step, pas pendant.

1. **Portée du journal d'audit.** Événements auth uniquement, ou aussi les
   mutations métier (`entity` CRUD) ? Reco : auth + admin (rôles, statut,
   sessions) pour V2.3 ; un hook générique `@Audited()` pour les entités
   métier est un step V2.4 si besoin.
2. **Acteur d'un événement système.** Login échoué, expiration de token :
   `actorId` = l'utilisateur concerné, ou `null` (système) ? Reco :
   l'utilisateur concerné quand il est identifiable (login échoué → on
   connaît l'email tenté, pas forcément un `userId`), sinon `null` +
   `actorEmail` en clair.
3. **Révocation de session ciblée.** « Déconnecter cet appareil précis »
   (révoque une famille de refresh token) en plus de « tout sauf
   celui-ci » ? Reco : oui — la famille est déjà le bon grain.
4. **Stockage du choix de langue.** `localStorage` seul, ou aussi
   `user.locale` en base (sync au login / au changement) ? Reco : les deux
   — `localStorage` pour l'invité, `PATCH /users/me { locale }` pour le
   compte (et c'est cette valeur qui sert aux e-mails).
5. **Clé de traduction manquante.** Fallback silencieux sur `en`, ou
   afficher la clé ? Reco : fallback sur `en` en prod, afficher la clé en
   dev (`missingHandler`).
6. **`<lib-async-button>` : projection ou wrapper ?** Directive
   `libAsyncButton` sur un `<button mat-*>` existant (garde le style
   Material), plutôt qu'un composant qui ré-enrobe. Reco : directive +
   input `[loading]`.
7. **Sous-nav à onglets `/app/admin`.** Nouvelle route parente
   `/app/admin` avec `<mat-tab-nav-bar>` (Users / Roles / Audit) et les
   pages en routes enfants, ou garder 3 entrées de menu ? Reco : onglets —
   une seule entrée de menu « Admin », 3 onglets. Les bricks
   `frontend-admin-users` / `role` / `audit` enregistrent leur onglet.

## Principes (repris de V1 / V2 / V2.1 / V2.2)

- Chaque step : analyser l'existant, implémenter **uniquement** son
  périmètre, `nx run-many -t lint test build typecheck` vert, remplir le
  « Résumé d'implémentation » + le coût tokens en fin de step.
- Briques opt-in via generators `tools/starter-plugin`, idempotents,
  jamais imposées au runtime.
- Config uniquement via `AppConfigService` — jamais `process.env` hors
  `libs/backend/core/config`. Toute nouvelle variable → `ENVIRONMENT_VARIABLE_NAMES`
  + `validate-env.ts` + getter + `.env.example` + tableau README + les deux
  specs.
- Contrats front/back dans `libs/shared/contracts`.
- Registre npm public (`.npmrc` posé en V2.2). Nouvelle dépendance runtime
  seulement si la stdlib / Angular / Material ne suffit pas — et ajoutée à
  la fois au `package.json` racine et à celui de la brick.
- Pas de Redis, pas de Sentry, pas d'observabilité externe (inchangé — le
  step 50 « client error reporting » est explicitement hors périmètre
  V2.3).
- Frontend zoneless : ouvrir un `MatDialog` **synchrone** dans le handler,
  pas dans un callback async ; `MatDialog` n'expose pas `role="dialog"`
  côté Playwright.

# STEP 45 — Journal d'audit

## Objectif

Tracer les actions sensibles (auth + admin) dans une collection
append-only, consultable et filtrable depuis la console admin. Best-effort :
un échec d'écriture d'audit ne casse jamais l'action tracée.

## Emplacement

- `libs/backend/features/audit/` (nouvelle lib, pattern `entity`) — schéma,
  service, listeners, controller admin-only.
- `libs/backend/auth/src/lib/` + `libs/backend/features/user/src/lib/` —
  émission de nouveaux événements (`AuthEvents` / `UserEvents` étendus, ou
  un `AuditEvents` dédié consommé par le brick audit).
- `libs/shared/contracts/src/lib/audit.ts` (nouveau).
- `libs/frontend/features/admin-audit/` (nouvelle lib, miroir
  `admin-roles`) — page `/app/admin/audit`.

## Dépendances

Brick `auth` (source des événements). `role` optionnel (filtre par acteur).

## Fonctionnalités

- Collection `audit_events` :
  `{ actorId?, actorEmail?, action, target?, targetType?, ip?, userAgent?,
  meta?, at }`. Index `(actorId, at)`, `(action, at)`, `at` (TTL selon
  `AUDIT_RETENTION_DAYS`).
- `AuditService.record(event)` — fire-and-forget, log l'erreur, ne throw
  jamais.
- Listeners branchés sur : `auth.login` (succès + échec),
  `auth.logout`, `auth.password-changed`, `auth.2fa-enabled` /
  `auth.2fa-disabled`, `auth.token-reused` (alerte sécurité),
  `user.roles-changed`, `user.status-changed`, `identity.linked` /
  `identity.unlinked`, `session.revoked-all` (step 46).
  → il faut **ajouter ces émissions** aux services concernés (elles
  n'existent pas toutes).
- `GET /api/audit` (admin-only, paginé) : filtres `actor`, `action`,
  `from` / `to` (dates), `sort=at&dir`.
- `GET /api/audit/actions` : la liste distincte des `action` connues (pour
  alimenter le filtre côté UI).
- Page `/app/admin/audit` : `<lib-data-table>`, colonne `at` en
  `<lib-relative-time>` (step 48 — d'ici là, ISO brute), acteur cliquable
  (filtre), `meta` en `<lib-json-viewer>` ou dépliable.

## Generator

Nouveau brick `audit` : `nx g @org/starter-plugin:audit` (exige `auth`).
Copie la lib backend + la lib frontend `admin-audit` si `frontend-admin-users`
présent, wire `AuditModule` dans `app.module`, ajoute l'onglet/route
`/app/admin/audit`, enregistré dans `generators.json`.

## Config

`AUDIT_RETENTION_DAYS` (défaut `90`, `0` = pas de TTL) — ajoutée partout
(env vars + validate + getter + `.env.example` + README + specs).

## Contraintes

- `record()` ne doit jamais faire échouer l'action tracée ni la ralentir
  sensiblement (écriture async non attendue, ou `void`).
- Aucune donnée secrète dans `meta` (pas de mot de passe, pas de token, pas
  de secret TOTP) — le service filtre une liste de clés interdites.
- Le brick `auth` n'importe **pas** `@org/backend-features-audit` : il émet
  des événements, le brick audit s'y abonne (comme `auth-reset`).

## Critères d'acceptation

- Un login, un changement de mot de passe, un changement de rôle et une
  désactivation de compte produisent chacun une ligne d'audit avec le bon
  `actorId` / `action` / `target`.
- Une panne d'écriture Mongo sur `audit_events` (mockée) ne fait pas
  échouer le login.
- `GET /api/audit?actor=<id>&action=auth.login` filtre correctement,
  `403` sans le rôle admin.
- `nx run-many -t lint test build typecheck` vert + E2E « une action admin
  apparaît dans le journal ».

## Décision de lancement

Points 1 (portée) et 2 (acteur système) tranchés : **auth + admin**
(login/logout/password/2FA/token-reuse/identity + rôles/statut), pas les
mutations d'entités métier ; acteur = l'utilisateur concerné quand
identifiable (login échoué → `actorEmail` en clair, `actorId: null`),
sinon `null`. Ajout : l'acteur des actions authentifiées est renseigné par
un **`RequestActorInterceptor`** (brick auth, `APP_INTERCEPTOR`) qui copie
`request.user` dans un `RequestContextService` étendu — les services
restent sans paramètre `actor`.

## Résumé d'implémentation

### Config — `libs/backend/core/`

`AUDIT_RETENTION_DAYS` (non-negative int, `0` = pas de TTL, défaut 90) —
`environment-variables.ts` + `ENVIRONMENT_VARIABLE_NAMES` + nouveau
`parseOptionalNonNegativeInt` dans `validate-env.ts` + getter
`AppConfigService.audit`. `RequestContextService` : `RequestStore` gagne
`actor?: RequestActor`, méthodes `setActor()` / `get actor`.

### Contrats — `libs/shared/contracts/src/lib/audit.ts` (nouveau)

`AuditEvent` (`{ id, actorId, actorEmail, action, target, targetType, ip,
userAgent, meta, at }`, champs nullables), `PaginatedAuditEvents`.

### Backend auth / user — émission d'événements

- **`auth-events.ts`** : `AuthEvents` gagne `loginSucceeded`,
  `loginFailed`, `passwordChanged`, `twoFactorEnabled/Disabled`,
  `tokenReused`, `identityLinked/Unlinked`.
- **`user-events.ts`** : `UserEvents` gagne `rolesChanged`, `statusChanged`.
- `auth.service.ts` (`login` succès + les 3 échecs via un helper `fail`,
  `changePassword`), `two-factor.service.ts` (`confirm` / `disable` — +
  `AuthEvents` injecté), `two-factor.controller.ts` / `oidc.controller.ts`
  (login réussi 2FA / OIDC — + `AuthEvents` injecté),
  `refresh-token.service.ts` (reuse — + `AuthEvents` injecté),
  `identity.service.ts` (link / unlink — + `AuthEvents` injecté),
  `user.service.ts` (`setRoles` / `setStatus`).
- **`request-actor.interceptor.ts`** (nouveau) + `APP_INTERCEPTOR` dans
  `auth.module.ts`.

### Backend — `libs/backend/features/audit/` (nouvelle lib, scaffold `entity audit`)

- **`audit.schema.ts`** : collection `audit_events`, index `(actorId, at)`,
  `(action, at)` ; le TTL est créé au bootstrap.
- **`audit.repository.ts`** : `distinctActions()`, `syncRetentionIndex(days)`
  (drop/recrée l'index `at_ttl`).
- **`audit.service.ts`** : `record()` fire-and-forget (jamais throw, remplit
  actor/ip/ua depuis `RequestContextService`, `sanitizeMeta` retire
  `pass|secret|token|otp|code|credential`), `list()` (filtres actor / action
  substring / from-to), `actions()` ; `onApplicationBootstrap` →
  `syncRetentionIndex`.
- **`audit-actions.ts`** : constantes `AUDIT_ACTION`.
- **`audit.listeners.ts`** : `onModuleInit` abonne `AuditService.record` à
  tous les events `AuthEvents` + `UserEvents`.
- **`audit.controller.ts`** : `@Roles('admin')`, `GET /audit`,
  `GET /audit/actions`.
- **`audit.module.ts`** : importe `AuthModule` + `UserModule` (pour les
  emitters — jamais l'inverse), `forFeature(AuditEvent)`.

### Frontend — `libs/frontend/features/admin-audit/` (nouvelle lib, miroir `admin-roles`)

`admin-audit.service.ts` (mappe `DataQuery` → `?actor` / `?action` / `?dir`),
`admin-audit-page.ts` (`<lib-data-table>`, colonnes When/Actor/Action/
Target/IP, `at` via `DatePipe`, filtres actor + action).

### Frontend — app

`app.routes.ts` : route `admin/audit`. `dashboard-nav.ts` : entrée
« Audit ». `tsconfig.base.json` + `apps/frontend/tsconfig.{app,spec}.json`.

### Générateur — `tools/starter-plugin/src/generators/audit/` (nouveau)

`nx g @org/starter-plugin:audit` (exige `auth`) : copie la lib, wire
`AuditModule`, `apps/backend/package.json`, et — si `frontend-admin-users`
présent — copie `admin-audit`, route + nav + refs tsconfig. Idempotent.
`generators.json`. Spec `generator.spec.ts` (5 cas).

### Vérification

`nx run-many -t lint test build typecheck` : **26/26 projets verts** (2
nouveaux : `backend-features-audit`, `frontend-features-admin-audit`).
Nouveaux specs : `audit.e2e.spec.ts` (vrai Mongo — login ok/ko, changement
de rôle attribué à l'admin, admin-only, `/audit/actions`),
`audit.service.spec.ts` (best-effort + sanitize + contexte),
`admin-audit.service.spec.ts`, `admin-audit-page.spec.ts`, `audit`

# STEP 46 — Sessions & appareils

## Objectif

Rendre visibles et révocables les sessions d'un compte. Toute la mécanique
existe (`RefreshTokenService.revokeAllForUser` / `revokeAllForUserExcept`,
familles de tokens) mais n'est branchée sur aucune route ni aucun écran.

## Emplacement

- `libs/backend/auth/src/lib/refresh/` — projection « session », révocation
  ciblée par famille, `lastUsedAt`.
- `libs/backend/auth/src/lib/auth.controller.ts` (ou nouveau
  `sessions.controller.ts`) — `GET/DELETE /api/auth/sessions`.
- `libs/frontend/features/profile/src/lib/` — section « Appareils ».
- `libs/frontend/features/admin-users/` — action « révoquer les sessions ».
- `libs/shared/contracts/src/lib/auth.ts` — `SessionInfo`.

## Dépendances

Brick `auth`. Section profil : brick `frontend-auth --profile` (V2.1).
Action admin : `frontend-admin-users`.

## Fonctionnalités

- `refresh_tokens` : `lastUsedAt` mis à jour à chaque rotation réussie
  (aujourd'hui seule la révocation est datée).
- `RefreshTokenRepository.listActiveForUser(userId)` → une entrée par
  **famille** vivante : `{ familyId, userAgent, ip, createdAt, lastUsedAt,
  current: boolean }`.
- `RefreshTokenService.revokeFamily(familyId, userId)` (vérifie
  l'appartenance) — la révocation ciblée.
- `GET /api/auth/sessions` (bearer) → `SessionInfo[]`, `current` marque la
  session dont le refresh cookie est présenté.
- `DELETE /api/auth/sessions/:familyId` (bearer + CSRF, car cookie) →
  révoque cette famille. `409` si c'est la session courante (utiliser
  `/logout`).
- `DELETE /api/auth/sessions` (bearer + CSRF) → « déconnecter partout sauf
  ici » (= `revokeAllForUserExcept`).
- `POST /api/users/:id/revoke-sessions` (admin-only) → `revokeAllForUser` +
  émet `session.revoked-all` (audité au step 45).
- Profil : section « Appareils » — liste, badge « Cet appareil », bouton
  « Déconnecter » par ligne, bouton « Déconnecter partout ».
- Admin users : action ligne « Révoquer les sessions » (confirm dialog).

## Generator

Aucun nouveau brick — modifs dans `auth` (copié tel quel), `profile` et
`admin-users` (copiés tels quels). Aucun changement de générateur.

## Config

Aucune nouvelle variable.

## Contraintes

- La projection par famille ne doit pas révéler le token ni son hash.
- `lastUsedAt` : un `updateOne` léger sur la rotation, pas un document
  rechargé.
- `DELETE /api/auth/sessions/:familyId` refuse la famille courante (sinon
  l'utilisateur se déconnecte sans le vouloir depuis l'écran « Appareils »).

## Critères d'acceptation

- Ouvrir 2 sessions (2 navigateurs), en révoquer une depuis l'autre :
  la session révoquée échoue au prochain `/refresh` (`401`), l'autre
  continue.
- « Déconnecter partout » depuis la session A : B et C meurent, A survit.
- Action admin : toutes les sessions de la cible meurent, ligne d'audit
  `admin.sessions-revoked`.
- `nx run-many -t lint test build typecheck` vert + E2E « voir mes
  sessions, en révoquer une ».

## Décision de lancement

Points 3 (révocation ciblée) tranché : **oui**, par famille. Ajustements :
routes sous `auth/sessions` (nouveau `SessionsController` dans la brick
auth), **bearer-only sans CSRF** (comme `change-password` / identities — le
cookie n'est que *lu* pour marquer la session courante). Champ
`sessionStartedAt` ajouté au schéma `refresh_tokens` (reporté à chaque
rotation) plutôt qu'un `lastUsedAt` — le `createdAt` du token vivant fait
déjà office de « dernière activité ».

## Résumé d'implémentation

### Contrats — `libs/shared/contracts/src/lib/auth.ts`

`SessionInfo` (`{ id, ip, userAgent, createdAt, lastUsedAt, current }`).

### Backend auth — `libs/backend/auth/src/lib/refresh/`

- **`refresh-token.schema.ts`** : `sessionStartedAt?: Date`.
- **`refresh-token.repository.ts`** : `findLiveForUser(userId)` (tokens
  non-révoqués / non-expirés, tri desc), `revokeFamilyForUser(userId,
  family)` (vérifie l'appartenance → `false` sinon).
- **`refresh-token.service.ts`** : `issue()` 4ᵉ arg `sessionStartedAt` ;
  `rotate()` le reporte (`existing.sessionStartedAt ?? existing.createdAt`).
  Nouveaux `listSessions(userId, currentToken?)` (dédup par famille,
  `current` = hash du cookie), `familyOfToken(token)`,
  `revokeSession(userId, family)` (`404 SESSION_NOT_FOUND`).
- **`sessions/sessions.controller.ts`** (nouveau, `@Controller('auth/sessions')`)
  : `GET /`, `DELETE /` (autres sessions), `DELETE /:familyId` (`409
  SESSION_IS_CURRENT`), `POST /revoke/:userId` (`@Roles('admin')`, émet
  `emitSessionsRevoked`). Enregistré dans `auth.module.ts`.
- **`auth-events.ts`** : `AuthEvents.emitSessionsRevoked` / `onSessionsRevoked`.

### Backend audit — `libs/backend/features/audit/`

`AUDIT_ACTION.SESSIONS_REVOKED = 'admin.sessions-revoked'` + listener
`onSessionsRevoked` (acteur = l'admin via le contexte).

### Frontend — `libs/frontend/features/profile/`

`profile.service.ts` : `listSessions` / `revokeSession` /
`revokeOtherSessions`. `profile-page.ts` : panneau « Devices » (liste,
badge « This device », « Sign out » par ligne sauf la courante, « Sign out
everywhere else »).

### Frontend — `libs/frontend/features/admin-users/`

`admin-users.service.ts` : `revokeSessions(userId)`. `admin-users-page.ts`
: action de ligne « Sessions » (confirm dialog).

### Générateur

Aucun changement : modifs dans `auth` / `audit` / `profile` / `admin-users`
(copiés tels quels par leurs generators).

### Config

Aucune nouvelle variable.

### Vérification

`nx run-many -t lint test build typecheck` : **26/26 verts**. `backend-auth`
23 suites / 191 tests (bloc `sessions / devices` dans `auth.e2e.spec.ts` :
liste + current, révocation ciblée + 401 au refresh suivant, `409`
courante, `404` non-propriétaire, « sign out everywhere else », révoke
admin + `403` non-admin). Frontend : `profile-page.spec.ts` (+2 tests
devices), `admin-users-page.spec.ts` (+1). E2E Playwright
`sessions.spec.ts` (2 contextes navigateur : voir mes appareils, en
déconnecter un → l'autre revient à `/login` au reload) ; régressions
`connected-accounts` / `two-factor` / `admin` vertes.

### Coût tokens

≈ 170k tokens sur la fenêtre de contexte pour ce step.

# STEP 47 — i18n (Transloco)

## Objectif

Internationaliser le frontend (`fr` / `en` fournis) et les e-mails
transactionnels, avec un sélecteur de langue dans le shell et un choix
persisté.

## Emplacement

- `libs/frontend/i18n/` (nouvelle lib toujours-présente-si-installée, ou
  brick `frontend-i18n`) — `provideI18n()`, `TranslocoService`,
  `<lib-lang-switcher>`, fichiers `assets/i18n/{en,fr}.json`.
- Toutes les libs `libs/frontend/**` — remplacement des chaînes en dur par
  `| transloco` / clés.
- `libs/backend/mailer/src/lib/templates/render.ts` +
  `libs/backend/auth-reset/` — renderers paramétrés par `locale`.
- `libs/backend/features/user/src/lib/user.schema.ts` — champ `locale?`.
- `libs/shared/contracts` — `locale` sur `UserProfile` / `UpdateProfileRequest`.

## Dépendances

`@jsverse/transloco` (nouvelle dépendance). Brick `frontend-design` (shell
+ Material pour le switcher). E-mails localisés : brick `mailer`.

## Fonctionnalités

- `provideI18n()` dans `app.config.ts` : langues `['en','fr']`, défaut
  `en`, `reRenderOnLangChange: true`, `missingHandler` (clé en dev,
  fallback `en` en prod).
- Détection au démarrage : `user.locale` → `localStorage['locale']` →
  `navigator.language` (préfixe) → `en`. Le `TranslocoService` est setté
  avant le premier rendu (APP_INITIALIZER / `provideAppInitializer`).
- `<lib-lang-switcher>` : `mat-menu` dans la topbar du shell (à côté du
  menu compte). Change la langue, écrit `localStorage`, et si connecté
  `PATCH /users/me { locale }`.
- `assets/i18n/en.json` + `fr.json` : toutes les chaînes visibles des

  passe `user.locale ?? 'en'`.
- `user.locale` : `PATCH /users/me` l'accepte (`'en' | 'fr'`), `toUserProfile`

## Generator

Brick `frontend-i18n` : `nx g @org/starter-plugin:frontend-i18n` (exige

## Config

Aucune variable backend obligatoire (`locale` vit sur le user).
`MAIL_DEFAULT_LOCALE` optionnelle (défaut `en`) pour les e-mails sans
utilisateur identifié — à trancher au lancement (probablement inutile).

## Contraintes

- Aucune régression : sans le brick i18n, le texte anglais en dur reste
  affiché (les composants livrent un fallback, ou les clés par défaut
  sont l'anglais).
- Le switcher n'apparaît que si ≥ 2 langues sont configurées.
- Les tests unitaires des composants doivent fournir un `TranslocoTestingModule`
  (ou un mock) — prévoir un helper dans `frontend-i18n/testing`.
- SSR non concerné (hors périmètre) mais ne pas coder de manière qui
  l'empêcherait (pas de `window` au module scope).

## Critères d'acceptation

- Basculer `en` → `fr` depuis le switcher : toute l'UP visible change,

- Un compte avec `locale: 'fr'` reçoit l'e-mail de reset en français.
- `nx run-many -t lint test build typecheck` vert + E2E « changer de
  langue, vérifier une page traduite, reload ».

# STEP 49 — Shell UX

## Objectif

Trois améliorations transverses du shell : progression de navigation,
protection des formulaires non enregistrés, et regroupement de la console
admin en onglets.

## Emplacement

- `libs/frontend/dashboard/src/lib/` — barre de progression, sous-nav.
- `libs/frontend/core/src/lib/` (ou `frontend-ui`) — guard
  `canDeactivate` + interface `FormComponent`.
- `apps/frontend/src/app/app.routes.ts` — regroupement `/app/admin`.
- Generators `frontend-admin-users`, `role`, `audit` — enregistrement
  d'onglet.

## Dépendances

Brick `frontend-dashboard`. Le regroupement onglets touche
`frontend-admin-users` / `role` (44) / `audit` (45).

## Fonctionnalités

- **Barre de progression** : un `<mat-progress-bar>` fin en haut du shell,
  actif pendant les `NavigationStart`→`NavigationEnd`/`Cancel`/`Error` et
  (optionnel) pendant qu'au moins une requête HTTP « longue » est en vol
  (via un `LoadingService` + un interceptor qui compte, avec un délai
  anti-flicker de 150 ms).
- **Guard `canDeactivate`** : `unsavedChangesGuard` générique — un
  composant expose `hasUnsavedChanges(): boolean` (ou un signal), le guard
  ouvre un `DialogService.confirm` avant de quitter. Appliqué au profil et
  au role-form (si transformé en page).
- **Sous-nav admin à onglets** : route `/app/admin` avec
  `<mat-tab-nav-bar>` + `<router-outlet>`, enfants `users` / `roles` /
  `audit`. Une seule entrée `DASHBOARD_NAV` « Admin ». Chaque brick admin
  enregistre son onglet via un token `ADMIN_TABS` (multi-provider) plutôt
  qu'en patchant un fichier.

## Generator

- `frontend-dashboard` : livre la barre de progression + le composant de
  sous-nav + le token `ADMIN_TABS`.
- `frontend-admin-users` / `role` / `audit` : au lieu d'ajouter une entrée
  `DASHBOARD_NAV` + une route à plat, poussent un `ADMIN_TABS` entry et une
  route enfant sous `/app/admin`. **Refacto des generators existants** —
  idempotence et migration d'un projet déjà généré à vérifier.

## Config

Aucune.

## Contraintes

- La barre de progression ne doit pas « flickering » sur les navigations
  instantanées (délai d'apparition).
- Le guard ne se déclenche pas sur une soumission réussie (le composant
  remet son état à « clean » après save).
- Migration : un projet ayant déjà `frontend-admin-users` + `role` généré
  à plat doit pouvoir lancer la nouvelle version des generators sans
  casser ses routes (ou une note de migration explicite).

## Critères d'acceptation

- Naviguer entre deux pages `/app/**` montre brièvement la barre.
- Modifier le profil sans enregistrer puis cliquer « Home » → dialog de
  confirmation ; enregistrer puis naviguer → pas de dialog.
- `/app/admin` affiche 3 onglets (Users / Roles / Audit), une seule entrée
  de menu.
- `nx run-many -t lint test build typecheck` vert ; E2E `dashboard`,
  `admin`, `roles` adaptés et verts.

## Résumé d'implémentation

_À faire._

- **RBAC permissions granulaires** — `Role.permissions` + guard
  `@RequirePermissions()`. Les rôles simples suffisent tant qu'un projet

  alternative maison à Sentry, à faire si le besoin d'observabilité
  frontend se confirme.

- Command palette (Cmd-K), centre de notifications, impersonation admin.
- Avatar + upload de fichier (nécessite une décision « brick stockage »).
- Data-table : sélection multiple + actions groupées, export CSV, colonnes
  masquables, vues sauvegardées.
- 3ᵉ langue / lazy scopes Transloco, SSR/hydration, PWA offline.
- Audit des mutations métier (`@Audited()` sur les entités `entity`).
- Tout ce qui était déjà hors périmètre V2.1/V2.2 (Redis, observabilité
  externe, multi-tenant, client API généré depuis l'OpenAPI).
