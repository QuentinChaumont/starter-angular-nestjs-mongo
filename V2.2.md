# Starter Nx Angular + NestJS + Mongo — V2.2

## Objectif

La V2.1 a livré l'auth durcie (rate-limit, admin-only), le mailer, le reset
mot de passe, le profil, la console admin et le CI/Docker. L'OIDC reste
mono-provider (une seule paire issuer/clientId configurée via
`OIDC_ISSUER` etc.), et les rôles sont des chaînes libres codées en dur —
il n'y a pas de vraie gestion.

La **V2.2** creuse l'authentification :

1. **2FA / TOTP** — activable/désactivable par chaque utilisateur depuis
   son profil.
2. **Connexions sociales (Google) + Keycloak**, en plus de l'OIDC
   générique déjà présent — sans dupliquer le moteur OIDC.
3. **Liaison de comptes** — un même utilisateur doit pouvoir se connecter
   avec son mot de passe local **et** Google **et** Keycloak, tous liés
   au même compte, gérable depuis le profil (« Connected accounts »).
4. **Gestion des rôles** — un vrai CRUD (création / modification /
   suppression) au lieu de chaînes codées en dur, exposé dans la console
   admin.

Le starter reste **modulaire** : un projet qui n'installe pas le brick
auth (ou qui n'active aucun provider OIDC) garde le comportement actuel
inchangé.

---

## Décisions d'architecture V2.2 (déjà tranchées)

Ces choix s'appliquent à toutes les étapes ci-dessous. Ne pas les
réinterroger pendant l'implémentation.

### Rôles — noms simples, pas de permissions granulaires

Un `Role` reste `{ name, description }`. `RolesGuard` continue de
comparer des **noms** de rôle (`@Roles('admin')`), inchangé. La nouvelle
collection `Role` est la source de vérité pour la console admin (liste
des rôles assignables) mais n'introduit pas de moteur de permissions
(`roles:write`, `users:read`, …) — hors périmètre V2.2, à reconsidérer en
V3 si un projet dérivé en a vraiment besoin.

### 2FA — optionnel pour tout le monde

Pas d'enforcement serveur (« les admins doivent activer le 2FA »). Chaque
compte active/désactive le TOTP depuis son profil, quel que soit son
rôle. Applicable aussi bien à un compte local qu'à un compte lié
uniquement à un provider OIDC — l'étape TOTP s'insère après **n'importe
quel** login réussi (password ou OIDC) si `twoFactorEnabled` est vrai sur
le compte.

### Keycloak — documentation uniquement, pas de service docker-compose

Pas de conteneur Keycloak ajouté à `docker-compose.yml`. Le starter
documente (README) comment pointer les variables `OIDC_KEYCLOAK_*` vers
un realm Keycloak existant (local ou distant). Un projet qui veut tester
en local ajoute son propre service Keycloak dans son
`docker-compose.override.yml`.

---

## À trancher avant implémentation

Ces points ne sont **pas** encore décidés — les arbitrer au lancement de
chaque step, pas pendant l'implémentation.

1. **Forme de la config multi-provider.** Registre générique N-providers
   (une variable JSON `OIDC_PROVIDERS`) vs. trois **emplacements fixes** :
   `OIDC_*` (générique/custom, déjà là), `OIDC_GOOGLE_CLIENT_ID` /
   `OIDC_GOOGLE_CLIENT_SECRET` (issuer + scopes pré-remplis), et
   `OIDC_KEYCLOAK_ISSUER` / `_CLIENT_ID` / `_CLIENT_SECRET`. Reco :
   emplacements fixes — colle exactement au besoin (3 providers connus),
   reste validable par `class-validator` comme le reste de
   `environment-variables.ts`, pas de parsing JSON custom. Un vrai
   registre N-providers peut être un futur refactor si un 4ᵉ provider
   apparaît.
2. **Modèle de liaison de comptes.** Nouvelle collection `identities`
   (`userId`, `provider`, `subject`, `linkedAt`) séparée de `User`, plutôt
   que le lien actuel « par email » codé dans `OidcUserLinker`. Reco :
   `identities` — c'est le seul moyen de lier plusieurs providers + local
   à un même compte sans collision sur l'email.
3. **Rôles système protégés.** `admin` (et `user` si présent en seed) ne
   doivent pas pouvoir être renommés/supprimés depuis le CRUD (casserait
   `seed-admin` et les guards codés en dur ailleurs). Reco : flag
   `system: true` sur ces rôles, CRUD renvoie 409 sur rename/delete.
4. **Dernier moyen de connexion.** Un compte 100 % SSO (pas de mot de
   passe local) qui délie son seul provider restant devient
   inconnectable. Reco : bloquer côté API la suppression du dernier
   identifiant de connexion (password absent + une seule identity) avec
   un message explicite.
5. **Lib TOTP.** Pas de dépendance 2FA existante. Reco : `otplib`
   (RFC 6238, léger, zéro dépendance native) + `qrcode` pour le rendu du
   QR code en data-URI côté profil.
6. **Sync des rôles OIDC → rôles locaux.** Le `rolesClaim` actuel importe
   les rôles depuis le token **à la création** du compte seulement. Reco :
   comportement inchangé (pas de resync à chaque login) — une fois créé,
   un compte est géré via le CRUD de rôles local, pas via le realm
   Keycloak, pour éviter un conflit entre les deux sources de vérité.

## Principes (repris de V1 / V2 / V2.1)

- Chaque step : analyser l'existant, implémenter **uniquement** son
  périmètre, `nx run-many -t lint test build typecheck` vert, remplir le
  « Résumé d'implémentation » + le coût tokens en fin de step.
- Briques opt-in via generators `tools/starter-plugin`, idempotents,
  jamais imposées au runtime.
- Config uniquement via `AppConfigService` — jamais `process.env` hors
  `libs/backend/core/config`. Toute nouvelle variable ajoutée à
  `ENVIRONMENT_VARIABLE_NAMES` + `.env.example` + tableau README.
- Contrats front/back dans `libs/shared/contracts`.
- Pas de Redis, pas de Sentry, pas d'observabilité (inchangé).

# STEP 39 — Registre multi-provider OIDC (fondation)

## Objectif

Généraliser `resolveOidcConfig` (un seul issuer/clientId global) vers
plusieurs providers OIDC actifs simultanément, chacun avec ses propres
routes de login/callback. Pré-requis dur des steps 40, 41 et 42 — aucun
provider concret n'est ajouté ici, seul le mécanisme l'est (le provider
« générique » actuel devient le premier provider du registre, comportement
inchangé pour un projet qui n'a que lui).

## Emplacement

- `libs/backend/auth/src/lib/oidc/` — `resolve-oidc-config.ts`,
  `oidc.controller.ts`, `oidc.service.ts`.
- `libs/shared/contracts/src/lib/auth.ts` — `OidcProviderInfo`.
- `libs/frontend/auth/src/lib/login/login-page.ts` — un bouton par
  provider actif au lieu d'un seul.

## Dépendances

Brique `auth` (OIDC générique, step V2) installée.

## Fonctionnalités

- `resolveOidcConfig` devient `resolveOidcProviders(config):
  ResolvedOidcProvider[]` — chaque entrée a un `id` (`generic`), un
  `label` (affiché sur le bouton), et la config actuelle. Absent →
  tableau vide (pas de régression).
- Routes `GET /api/auth/oidc/:providerId/login` et
  `GET /api/auth/oidc/:providerId/callback` (remplace les routes fixes
  actuelles ; `providerId=generic` reproduit le comportement existant).
  404 `OIDC_PROVIDER_UNKNOWN` si l'id ne correspond à aucun provider actif.
- `GET /api/auth/oidc/providers` (remplace `GET /auth/oidc/provider`) :
  retourne la liste `{ id, label, loginUrl }[]` des providers actifs.
- Front : `login-page.ts` affiche un bouton par provider retourné
  (au lieu du bouton unique actuel), même style.

## Generator

Pas de nouveau brick — le generator `auth` existant écrit directement la
version multi-provider (plus de version « historique » à maintenir en
parallèle).

## Config

Aucune nouvelle variable à ce step (les providers concrets arrivent aux
steps 40/41).

## Contraintes

- Rétrocompatible : un projet avec seulement `OIDC_ISSUER`/`OIDC_CLIENT_ID`
  garde exactement le même comportement (un seul bouton « Sign in with
  SSO »), juste via la nouvelle route `oidc/generic/login`.
- `oidc-callback.ts` (front) et `sanitize-relative-path.ts` (back) sont
  indépendants du provider — pas de changement.

## Critères d'acceptation

- Avec seulement le provider générique configuré : login end-to-end
  inchangé (E2E existant `frontend-e2e` toujours vert).
- `GET /api/auth/oidc/providers` avec 0 provider configuré → `[]`.
- `nx run-many -t lint test build typecheck` vert.

## Décision de lancement

Point 1 (« forme de la config multi-provider ») tranché : **emplacements
fixes**. Le step pose le registre avec la seule entrée `generic` (issue des
variables `OIDC_*` déjà présentes) ; Google et Keycloak s'ajouteront aux
steps 40/41 en append d'une entrée dédiée, sans parsing JSON.

## Résumé d'implémentation

### Backend — `libs/backend/auth/src/lib/oidc/`

- **`resolve-oidc-config.ts`** : `resolveOidcConfig()` (mono-provider,
  nullable) remplacé par `resolveOidcProviders(config): ResolvedOidcProvider[]`
  (+ `resolveOidcProvider(config, id)`). `ResolvedOidcProvider` =
  `ResolvedOidcConfig` + `{ id, label }`. La seule entrée construite
  aujourd'hui est `{ id: 'generic', label: 'SSO', … }` à partir des
  variables `OIDC_*` existantes ; trio incomplet → `[]` (pas de
  régression). Constante exportée `GENERIC_PROVIDER_ID`.
- **`oidc.service.ts`** : cache de client `openid-client` passé d'un
  singleton à une `Map<providerId, Promise<Client>>`. `createAuthRequest()`
  / `exchange()` prennent un `providerId` ; nouveau `requireProvider(id)`
  qui lève `NotFoundError('OIDC_PROVIDER_UNKNOWN')` (404) ;
  `listProviders(): { id, label }[]`. `isEnabled()` supprimé (plus utile).
- **`oidc.controller.ts`** : routes fixes remplacées par
  - `GET /api/auth/oidc/providers` → `{ id, label, loginUrl }[]`
    (remplace `GET /auth/oidc/provider`), `loginUrl` relatif à la base API
    (`/auth/oidc/:id/login`) ;
  - `GET /api/auth/oidc/:providerId/login` (404 `OIDC_PROVIDER_UNKNOWN`
    si l'id est inconnu) ;
  - `GET /api/auth/oidc/:providerId/callback` — vérifie que le
    `providerId` du cookie de transaction correspond à la route avant tout
    le reste (401 `OIDC_STATE_INVALID` sinon).
  Le contrôleur n'injecte plus `AppConfigService` (délégué au service).
- **`oidc-user.linker.ts`** : `linkFromClaims(providerId, claims)` — résout
  la config du provider concerné (`requireVerifiedEmail`, `rolesClaim` par
  provider). Lien toujours **par email vérifié** (la collection
  `identities` du step 42 remplacera ce lookup).
- **`cookies/auth-cookie.service.ts`** : `OidcTransaction` gagne un champ
  `providerId` (persisté + revalidé au parsing).

### Contrats — `libs/shared/contracts/src/lib/auth.ts`

`OidcProviderInfo` : `{ enabled, loginUrl }` → `{ id, label, loginUrl }`.
La liste vide vaut « aucun provider ».

### Frontend — `libs/frontend/auth/`

- **`auth.service.ts`** : `oidcProvider()` → `oidcProviders():
  Observable<OidcProviderInfo[]>` (fallback `[]`). `oidcLoginUrl(provider,
  redirectTo?)` préfixe la base API au `loginUrl` du provider.
- **`login/login-page.ts`** : bouton SSO unique → `@for` d'un bouton
  « Sign in with {{ label }} » par provider actif, même style
  `mat-stroked-button`.

### Docs

`README.md`, `libs/backend/auth/README.md`, `libs/frontend/auth/README.md`,
`.env.example` : routes per-provider, `OIDC_REDIRECT_URI` devient
`.../api/auth/oidc/generic/callback`. Aucune nouvelle variable
d'environnement (conforme au périmètre du step).

### Générateurs

Aucun changement : `auth` / `frontend-auth` copient les libs telles quelles
(`ensureLibCopied`), la version multi-provider est donc générée directement.

### Vérification

`nx affected -t lint test build typecheck` (base `HEAD`) : **22/22 projets
verts** (dont `backend-auth`, `frontend-auth`, `shared-contracts`,
`frontend`, `@org/backend`). `backend-auth` : 16 suites / 111 tests.

Specs mis à jour : `resolve-oidc-config.spec.ts`,
`oidc.controller.integration.spec.ts`, `oidc-user.linker.spec.ts`,
`cookies/auth-cookie.service.spec.ts`, `login-page.spec.ts` (front),
`auth.service.spec.ts` (front).

### Coût tokens

≈ 320k tokens sur la fenêtre de contexte pour ce step (lecture de
l'existant OIDC + generators, implémentation, mise à jour des specs et
docs, builds/tests).

# STEP 40 — Provider Google

## Objectif

Ajouter Google comme deuxième entrée du registre du step 39, en
« preset » : l'utilisateur du starter ne fournit qu'un `clientId` +
`clientSecret` (créés dans Google Cloud Console), tout le reste (issuer
`https://accounts.google.com`, scopes `openid profile email`) est
pré-rempli en dur.

## Emplacement

- `libs/backend/auth/src/lib/oidc/providers/google.ts` (nouveau) —
  construit un `ResolvedOidcProvider` à partir de
  `OIDC_GOOGLE_CLIENT_ID` / `OIDC_GOOGLE_CLIENT_SECRET`.
- `resolve-oidc-config.ts` — agrège générique + Google dans
  `resolveOidcProviders`.

## Dépendances

## Fonctionnalités

  (optionnelles) — provider actif seulement si les deux sont présentes.

# STEP 42 — Liaison de comptes (« Connected accounts »)

## Objectif

Permettre à un même utilisateur d'avoir plusieurs moyens de connexion liés
au même compte (mot de passe local + Google + Keycloak simultanément),
gérables depuis son profil, au lieu du lien actuel implicite « par email »
dans `OidcUserLinker`.

## Emplacement

- `libs/backend/features/user/src/lib/identity/` (nouveau) — schéma +
  service `identities`.
- `libs/backend/auth/src/lib/oidc/oidc-user.linker.ts` — bascule sur les
  identités au lieu du lookup par email.
- `apps/backend/.../auth.controller.ts` (ou nouveau
  `identities.controller.ts`) — `GET/POST/DELETE /api/auth/identities`.
- `libs/frontend/auth/src/lib/profile/` (ou équivalent existant du brick
  profil V2.1) — section « Connected accounts ».

## Dépendances

Steps 39 (+ 40 et/ou 41 pour avoir un provider à lier en pratique).

## Fonctionnalités

- Collection `identities` : `{ userId, provider (générique/google/
  keycloak), subject (sub du token), email, linkedAt }`, index unique
  `(provider, subject)`.
- `OidcUserLinker.linkFromClaims` : cherche d'abord une `identity`
  existante `(provider, subject)`. Sinon, si un compte avec le même email
  vérifié existe déjà → **lie** cette identity au compte existant (au lieu
  d'en créer un nouveau, comme aujourd'hui). Sinon → crée un nouveau
  compte + son identity.
- `GET /api/auth/identities` (authentifié) : liste des providers liés au
  compte courant + indique si un mot de passe local est défini.
- `POST /api/auth/identities/:providerId/link` : relance un flow OIDC
  (réutilise les routes du step 39) dont le callback, si l'utilisateur
  est déjà authentifié (cookie de session présent), lie l'identity au
  compte courant au lieu d'ouvrir une session.
- `DELETE /api/auth/identities/:providerId` : délie un provider. Refuse
  (409) si c'est le **dernier** moyen de connexion du compte (ni mot de
  passe local, ni autre identity restante).
- Page profil : liste des providers liés avec bouton « Connect » /
  « Disconnect » par provider actif globalement.

## Generator

Aucun nouveau brick — fait partie du generator `auth`.

## Config

Aucune nouvelle variable.

## Contraintes

- Migration : les comptes déjà créés via l'OIDC générique (avant ce step)
  n'ont pas d'`identity` — à la prochaine connexion OIDC, une `identity`
  est créée rétroactivement pour eux (lookup par email, comportement
  actuel, converti en `identity` au passage). Pas de script de backfill
  nécessaire.
- Lier un provider déjà lié à un **autre** compte → 409
  `IDENTITY_ALREADY_LINKED` (pas de vol de compte).

## Critères d'acceptation

- Un compte créé en local peut lier Google puis Keycloak, et se connecter
  ensuite avec n'importe lequel des trois.
- Délier le dernier moyen de connexion → 409, message explicite.
- `nx run-many -t lint test build typecheck` vert ; au moins un scénario
  E2E « link/unlink a provider » (avec un provider de test mocké — pas de
  vraie dépendance Google/Keycloak en CI).

# STEP 43 — 2FA / TOTP

## Objectif

Authentification à deux facteurs par code temporaire (RFC 6238), activable
par chaque utilisateur depuis son profil, indépendamment du provider de
connexion utilisé.

## Emplacement

- `libs/backend/auth/src/lib/two-factor/` (nouveau) — génération de
  secret, vérification TOTP, backup codes.
- `libs/backend/features/user/src/lib/user.schema.ts` — champs
  `twoFactorSecret` (chiffré, `select: false`), `twoFactorEnabled`,
  `twoFactorBackupCodes` (hashés).
- `libs/frontend/auth/src/lib/profile/` — section « Two-factor
  authentication » (activation avec QR code, saisie du code de
  confirmation, affichage unique des backup codes).
- `libs/frontend/auth/src/lib/login/` — étape de saisie du code après un
  login réussi si `twoFactorEnabled`.

## Dépendances

Aucune — indépendant de la chaîne OIDC (39-42).

## Fonctionnalités

- `POST /api/auth/2fa/setup` (authentifié) : génère un secret, retourne
  l'URI `otpauth://` + un QR code (data-URI) — secret pas encore persisté
  tant que non confirmé.
- `POST /api/auth/2fa/confirm` : vérifie le premier code saisi, persiste
  le secret (chiffré) + `twoFactorEnabled: true`, génère et retourne
  **une fois** 10 backup codes (hashés en base, comme les mots de passe).
- `POST /api/auth/2fa/disable` : désactive (mot de passe requis en
  re-confirmation).
- `AuthService.issueSession` : si `twoFactorEnabled`, le login
  (password ou OIDC) n'émet pas directement une session complète mais un
  **token intermédiaire** court (`pending_2fa`, quelques minutes) ;
  `POST /api/auth/2fa/verify` (avec ce token + le code TOTP ou un backup
  code) émet la vraie session.
- Un backup code est **à usage unique** (retiré de la liste après usage).

## Generator

Nouveau brick optionnel `two-factor` (ou intégré directement au brick
`auth` existant — à trancher au lancement du step selon la taille réelle
du diff). Reco par défaut : intégré à `auth` (le 2FA n'a pas de sens sans
lui), pas de brick séparé.

## Config

Aucune nouvelle variable (le secret de chiffrement du `twoFactorSecret`
réutilise `JWT_SECRET`, ou une nouvelle `TWO_FACTOR_ENCRYPTION_KEY` — à
trancher au lancement : dérivation depuis `JWT_SECRET` évite d'ajouter
une variable, reco par défaut).

## Contraintes

- Le secret TOTP n'est **jamais** renvoyé en clair après la confirmation
  initiale (comme un mot de passe).
- Les backup codes ne sont affichés **qu'une fois**, à la génération —
  la doc profil doit le dire explicitly.
- Un token `pending_2fa` ne doit donner accès à **aucune** route protégée
  autre que `/auth/2fa/verify`.

## Critères d'acceptation

- Activation : QR code scannable (vérifié avec une vraie app TOTP en
  test manuel), code confirmé → 2FA actif.
- Login avec 2FA actif : refusé sans code, accepté avec le bon code ou un
  backup code valide (une seule fois).
- `nx run-many -t lint test build typecheck` vert + tests unitaires sur
  la génération/vérification TOTP (vecteurs de test RFC 6238) + E2E
  « enable 2FA then login with code ».

## Résumé d'implémentation

# STEP 44 — Gestion des rôles (CRUD)

## Objectif

Remplacer les rôles « chaînes libres » codées en dur par une vraie
collection `Role`, avec un CRUD exposé dans la console admin — sans
toucher au fonctionnement de `RolesGuard` (toujours basé sur des noms).

## Emplacement

- `libs/backend/features/role/` (nouvelle lib, miroir de
  `libs/backend/features/user/`) — schéma, service, controller admin-only.
- `libs/shared/contracts/src/lib/role.ts` (nouveau).
- `libs/frontend/dashboard/.../admin/roles/` — page `/app/admin/roles`
  (liste via `<lib-data-table>`, création/édition/suppression).
- Console admin users existante — le champ rôles d'un user devient un
  multi-select alimenté par `GET /api/roles` au lieu d'un champ texte
  libre.

## Dépendances

Aucune — indépendant de la chaîne OIDC (39-42) et du 2FA (43).

## Fonctionnalités

- `Role { name (unique), description?, system: boolean, createdAt,
  updatedAt }`.
- `GET /api/roles` (paginé, admin-only) / `POST /api/roles` /
  `PATCH /api/roles/:id` / `DELETE /api/roles/:id`.
- Seed : `admin` créé en `system: true` par le script `seed-admin`
  existant (idempotent, comme aujourd'hui) si absent.
- `PATCH/DELETE` sur un rôle `system: true` → 409 `ROLE_SYSTEM_PROTECTED`.
- `DELETE /api/roles/:id` sur un rôle encore assigné à des users → 409
  `ROLE_IN_USE` (pas de suppression en cascade silencieuse) — l'admin
  doit d'abord retirer le rôle des users concernés.
- Assignation d'un rôle inexistant à un user (`PATCH /api/users/:id`) →
  400 (validation contre la collection `Role`).

## Generator

Nouveau brick optionnel `role` (même pattern que `entity` — CRUD miroir
front/back), câblé automatiquement si `auth` est installé (comme
`user`). Pas de generator séparé si `auth` est absent : pas de guard de
rôles à gérer sans lui.

## Config

Aucune nouvelle variable.

## Contraintes

- Migration douce : les `user.roles` existants (chaînes libres, jamais
  validées jusqu'ici) ne sont **pas** rétroactivement vérifiés contre la
  collection `Role` au démarrage — seule la validation à l'écriture
  (création/modification d'un user) est nouvelle. Un rôle orphelin
  préexistant reste actif tel quel (pas de perte d'accès surprise).
- `RolesGuard` inchangé (toujours une comparaison de noms) — ce step ne
  touche pas à l'autorisation, seulement à la gestion des rôles
  disponibles.

## Critères d'acceptation

- CRUD complet testable depuis `/app/admin/roles` : créer un rôle,
  l'assigner à un user depuis la console, le retirer, le supprimer.
- Suppression d'`admin` ou d'un rôle encore assigné → refusée avec un
  message clair.
- `nx run-many -t lint test build typecheck` vert + E2E « create role,
  assign to user, delete role ».
