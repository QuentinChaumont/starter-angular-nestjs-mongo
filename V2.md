# Starter Nx Angular + NestJS + Mongo — V2

## Objectif

La V1 a produit un socle backend complet et un ensemble de briques
optionnelles côté serveur (Mongo, CRUD, Auth JWT, Authorization, Security,
Health). Le frontend, lui, est resté un squelette (`app.routes.ts` vide,
`styles.scss` vide, `libs/frontend/core` sans contenu).

La V2 construit progressivement la **couche frontend du starter**, sur le
même principe que la V1 : des briques opt-in installées par des generators
Nx locaux, jamais imposées au runtime.

Briques ajoutées :

- **auth avancé backend** : refresh tokens + rotation + logout ;
- **login OIDC backend** : Authorization Code + PKCE, find-or-create user,
  émission du JWT maison ;
- **`frontend-design`** : Angular Material + CDK, thème Material 3
  (light/dark), charte graphique versionnée (`design.config.ts`) et
  `DESIGN.md` propre au projet ;
- **couleurs paramétrables** : hybride build-time (charte par défaut) +
  runtime (CSS custom properties, `ThemeService`, panneau de réglages UI,
  persistance `localStorage`) ;
- **`frontend-auth`** : écran de login, store d'auth (signals),
  intercepteur HTTP (bearer + `X-Request-Id` + refresh-on-401), guards de
  route, bouton de connexion OIDC ;
- **`frontend-dashboard`** : shell applicatif `MatSidenav` responsive
  devenant le layout par défaut des routes protégées ;
- **`frontend-feedback`** : gestion centralisée des popups (`DialogService`)
  et des notifications/toasts (`NotificationService`), branchées sur le
  format d'erreur `ApiError` de la V1 ;
- **`frontend-consent`** : popup légale de consentement (cookies / traceurs)
  affichée à l'arrivée sur le site, avec catégories, persistance du choix,
  re-consultation, et pages légales générées.

Le starter doit rester **modulaire** : un projet qui n'a besoin ni de
frontend riche, ni d'auth, ni de dashboard doit pouvoir ignorer toutes ces
briques et garder le socle V1 intact.

---

## Décisions d'architecture V2 (déjà tranchées)

Ces choix s'appliquent à toutes les étapes ci-dessous. Ne pas les
réinterroger pendant l'implémentation.

### Transport du refresh token — cookie httpOnly

- L'**access token** (JWT court, ~15 min) est renvoyé dans le corps de la
  réponse et gardé **en mémoire** côté Angular (jamais `localStorage`).
- Le **refresh token** est posé dans un cookie `httpOnly` + `Secure` +
  `SameSite=Lax`, scope path `/api/auth`. Le SPA n'y a jamais accès en JS.
- `POST /api/auth/refresh` lit le cookie, effectue la **rotation** (ancien
  token révoqué, nouveau émis), renvoie un nouvel access token.
- Protection CSRF de `/api/auth/refresh` et `/api/auth/logout` :
  **double-submit token**. À l'émission d'une session, le serveur pose
  aussi un cookie `csrf-token` **non-httpOnly** ; le SPA le recopie dans
  l'en-tête `X-CSRF-Token` sur ces deux routes ; le serveur compare.
- Impacts : CORS avec `credentials: true` (déjà géré par la brique
  Security, `CORS_ORIGINS`), et un `AuthCookieService` côté backend
  centralisant la pose/suppression des cookies.

### Packaging OIDC — intégré au brick auth, activé par la config

- Un seul brick auth backend et un seul brick `frontend-auth`.
- Le refresh/rotation/logout **et** OIDC font partie intégrante du brick
  auth (rien à gater, pas de flag). OIDC reste inerte tant que
  `OIDC_ISSUER` / `OIDC_CLIENT_ID` / `OIDC_REDIRECT_URI` ne sont pas
  configurés.
- Le login **local** (email + mot de passe, V1) et le login **OIDC**
  coexistent : en dev on peut travailler sans IdP.
- OIDC est un **fournisseur d'identité en amont** : après le callback, le
  starter crée/retrouve le `user` local et émet **son propre** JWT. Le
  token du provider OIDC n'est jamais renvoyé au client ni stocké.

### Couleurs paramétrables — hybride build + runtime

- `libs/frontend/design/src/lib/theme/design.config.ts` : source de vérité
  **versionnée** de la charte (couleurs de marque, rayons, densité,
  typo). Consommée au build pour générer les valeurs par défaut des CSS
  custom properties et le thème Material.
- Runtime : toutes les couleurs clés sont exposées en CSS custom
  properties (`--app-color-primary`, `--app-color-surface`, …) sur
  `:root`, chacune en `light-dark(<clair>, <sombre>)`. Le mode se pilote
  par un unique `color-scheme` sur `<html>` (`light` / `dark` /
  `light dark` = système). Un `ThemeService` bascule ce mode, surcharge
  des propriétés individuelles, et persiste le choix dans `localStorage`
  (`app.theme.*`), avec `try/catch` et repli sur la charte par défaut.
- Un composant `ThemeSettingsPanel` (dans la brique design) fournit l'UI
  de personnalisation ; le dashboard l'expose depuis son menu utilisateur.

### `frontend-dashboard` — shell par défaut

- Le generator réécrit `apps/frontend/src/app/app.ts` et `app.routes.ts` :
  - routes publiques (`/login`, `/auth/callback`) hors shell ;
  - routes applicatives regroupées sous `/app` derrière `authGuard`, à
    l'intérieur du `DashboardShellComponent` (toolbar + sidenav +
    `<router-outlet>`).
- Le menu latéral est **config-driven** (`DASHBOARD_NAV` : liste
  d'entrées `{ label, icon, route, roles? }`).
- Idempotent : relancer le generator ne duplique ni le shell ni les routes.

### Règles de développement (ajouts V2)

- Pas de librairie de state management externe (NgRx, etc.) : signals +
  services.
- Pas de framework de composants tiers autre qu'Angular Material / CDK.
- `libs/frontend/core` ne dépend **pas** de `@angular/material` : tout ce
  qui touche Material vit dans `frontend/design` ou au-dessus.
- Les composants consomment les **CSS custom properties**, jamais une
  couleur en dur ni un `$sass-var` de couleur de marque.
- `shared/contracts` reste sans dépendance Angular / Nest / Mongoose /
  Passport / openid-client.
- Le SPA ne stocke jamais de token en `localStorage` (access en mémoire,
  refresh en cookie httpOnly).
- Chaque brique frontend est installable indépendamment, avec un message
  d'erreur actionnable si un prérequis manque (comme les briques V1).
- Chaque étape doit compiler, `lint` + `test` + `build` doivent passer.
- Ne jamais développer une étape suivante par anticipation.

### Workflow attendu pour chaque step

Identique à la V1 :

1. analyser le code existant ;
2. proposer brièvement les fichiers créés / modifiés ;
3. implémenter uniquement le périmètre de l'étape ;
4. lancer `lint` / `test` / `build` pertinents (via `nx`) ;
5. corriger les erreurs ;
6. résumer les modifications dans le step ;
7. ajouter le coût en tokens de l'étape en fin de résumé ;
8. s'arrêter.

# STEP 21 — Auth avancé : refresh tokens, rotation, logout

## Objectif

Étendre `libs/backend/auth` (V1) avec une vraie gestion de session :
refresh token en cookie httpOnly, rotation, révocation, logout.

## Emplacement

```text
libs/backend/auth/src/lib/
├── refresh/
│   ├── refresh-token.schema.ts      // Mongo : userId, tokenHash, family, expiresAt, revokedAt, replacedBy, userAgent, ip
│   ├── refresh-token.repository.ts  // via BaseRepository<T>
│   └── refresh-token.service.ts     // issue / rotate / revoke / revokeAllForUser
├── cookies/
│   └── auth-cookie.service.ts       // pose/suppression cookies refresh + csrf
├── csrf/
│   └── csrf.guard.ts                // double-submit : compare cookie csrf-token et header X-CSRF-Token
└── auth.controller.ts               // + refresh / logout
```

## Dépendances

Aucune nouvelle dépendance npm. La lecture des cookies se fait avec un
parser interne minimal (`cookies/parse-cookies.ts`) ; leur pose utilise
`res.cookie()` natif d'Express. Cohérent avec l'ADN du repo (logger sans
lib, scrypt au lieu de bcrypt).

(`@nestjs/jwt`, `passport-jwt`, `@nestjs/mongoose` déjà là.)

## Fonctionnalités

- `POST /api/auth/login` (existant) : en plus du corps
  `AccessTokenResponse`, pose le cookie `refresh_token` (httpOnly, Secure,
  SameSite=Lax, path `/api/auth`) **et** le cookie `csrf-token`
  (non-httpOnly, même durée que le refresh).
- `POST /api/auth/refresh` :
  - protégé par `CsrfGuard` ;
  - lit le cookie, vérifie hash + expiration + non-révocation ;
  - **rotation** : révoque l'ancien (`revokedAt`, `replacedBy`), émet un
    nouveau refresh (même `family`), renvoie un nouvel access token ;
  - **détection de réutilisation** : si un token déjà révoqué est
    présenté, révoquer toute la `family` et répondre `401`.
- `POST /api/auth/logout` : protégé par `CsrfGuard`, révoque le refresh
  courant, efface les deux cookies.
- Refresh token : valeur aléatoire (`crypto.randomBytes`), stockée
  **hashée** (SHA-256) en base — jamais en clair.
- Durées via config : `JWT_EXPIRES_IN` (access, défaut `15m`),
  `REFRESH_EXPIRES_IN` (défaut `30d`).
- `RefreshTokenService.revokeAllForUser(userId)` exposé pour un futur
  « déconnecter partout ».
- Nettoyage : les tokens expirés depuis longtemps peuvent être purgés à la
  volée lors de la rotation (pas de cron en V2).

## Generator

Aucune modification du generator `auth` à ce step. Le brick copie la lib
entière et la câble dans `app.module.ts` comme avant ; le
refresh/rotation/logout fait désormais partie intégrante du brick auth (il
n'y a rien à *gater*, donc pas de flag `--refresh`). Pas de `main.ts` à
toucher (pas de `cookie-parser`).

## Config

Nouvelle variable :

| Variable | Requis | Défaut | Notes |
| --- | --- | --- | --- |
| `REFRESH_EXPIRES_IN` | non | `30d` | Lu seulement si auth installée |
| `AUTH_COOKIE_SECURE` | non | `true` en prod, `false` sinon | Permet le dev en http |

## Critères d'acceptation

- login pose les cookies attendus ;
- `refresh` sans cookie → `401` ; avec cookie valide → nouvel access
  token + nouveau cookie refresh (valeur différente) ;
- rejouer un refresh déjà tourné → `401` + famille révoquée ;
- `refresh` / `logout` sans `X-CSRF-Token` correct → `403` ;
- `logout` efface les cookies et révoque le token ;
- format d'erreur V1 respecté, `requestId` présent ;
- tests E2E : login → refresh → refresh (rotation) → reuse → logout ;
- tests unitaires `RefreshTokenService` et `CsrfGuard` ;
- `nx run-many -t lint,test,build` OK ;
- relancer le generator ne casse rien.

## Résumé d'implémentation

**Écarts assumés vs plan initial** : (1) pas de dépendance `cookie-parser`
— parser interne `cookies/parse-cookies.ts` + `res.cookie()` natif ;
(2) pas de flag `--refresh` sur le generator — le brick copie la lib

# STEP 22 — Login OIDC (Authorization Code + PKCE)

## Objectif

Permettre la connexion via un fournisseur OIDC générique (Keycloak,
Google, Azure AD…), en gardant l'émission du JWT maison.

## Emplacement

```text
libs/backend/auth/src/lib/oidc/
├── resolve-oidc-config.ts   // lit config.oidc ; null si non configuré
├── sanitize-relative-path.ts// anti open-redirect pour redirectTo
├── oidc-claims.ts           // type OidcClaims + extractRoles(claims, dot-path)
├── oidc.service.ts          // openid-client : discovery (lazy), authURL + PKCE, exchange
├── oidc-user.linker.ts      // link/create user local à partir des claims (par email vérifié)
└── oidc.controller.ts       // GET /auth/oidc/{provider,login,callback}
```

## Dépendances

```text
openid-client   ^5   (CJS — le backend NestJS est CommonJS)
```

Pas de Passport pour OIDC (on reste découplé, cf. principe V1).

## Fonctionnalités

- OIDC **fait partie du brick auth**, inerte tant que `OIDC_ISSUER` /
  `OIDC_CLIENT_ID` / `OIDC_REDIRECT_URI` ne sont pas configurés. Pas de
  flag `--oidc` (même logique que le refresh au step 21).
- `GET /api/auth/oidc/provider` → `OidcProviderInfo` (`enabled`,
  `loginUrl`) — le front affiche le bouton seulement si `enabled`.
- `GET /api/auth/oidc/login?redirectTo=/app/...` :
  - `state` + `nonce` + `code_verifier` (PKCE), stockés dans un cookie
    httpOnly `oidc_tx` (base64url JSON, path `/api/auth/oidc`, 10 min) ;
  - `redirectTo` assaini (chemin relatif à un seul `/` sinon défaut) ;
  - redirige (302) vers l'`authorization_endpoint`.
- `GET /api/auth/oidc/callback?code&state` :
  - efface `oidc_tx`, vérifie `state` contre le cookie ;
  - échange le `code` (+ `code_verifier`, `nonce`) via `openid-client`
    (qui valide la signature de l'`id_token` contre le JWKS) ;
  - `OidcUserLinker` : lien **par email vérifié** — réutilise le compte
    existant, sinon crée un compte sans mot de passe utilisable
    (mot de passe aléatoire haché) ; rôles depuis `OIDC_ROLES_CLAIM` ;
  - `AuthService.issueSession(user)` → access token + cookies refresh/csrf
    (réutilise le step 21) ;
  - redirige vers `OIDC_FRONTEND_URL + /auth/callback` avec
    `#access_token=...&expires_in=...&token_type=Bearer&redirect_to=...`
    (route dédiée du front — step 25 — qui consomme le fragment puis
    forwarde vers `redirect_to`).
- Le token du provider ne quitte jamais le backend.

## Generator

Aucune modification du generator `auth`. `openid-client` est dans les
`dependencies` du brick (installé avec lui). OIDC s'active par la config,
pas par un flag.

## Config

| Variable | Requis | Défaut | Notes |
| --- | --- | --- | --- |
| `OIDC_ISSUER` | pour activer | — | URL de discovery |
| `OIDC_CLIENT_ID` | pour activer | — | |
| `OIDC_REDIRECT_URI` | pour activer | — | `.../api/auth/oidc/callback` |
| `OIDC_CLIENT_SECRET` | non | — | Vide → client public + PKCE |
| `OIDC_SCOPES` | non | `openid profile email` | |
| `OIDC_FRONTEND_URL` | non | `http://localhost:4200` | Base des redirections |
| `OIDC_POST_LOGIN_REDIRECT` | non | `/app` | Chemin relatif par défaut |
| `OIDC_REQUIRE_VERIFIED_EMAIL` | non | `true` | Refuse un email non vérifié par l'IdP |
| `OIDC_ROLES_CLAIM` | non | — | Dot-path vers un claim `string[]` → rôles |

Toutes ignorées si le trio requis n'est pas là (`resolveOidcConfig` →
`null`).

## Contraintes

- Le token du provider OIDC ne sort jamais du backend.
- `redirectTo` : accepter seulement un chemin absolu à un seul `/`.
- Fonctionne à côté du login local — ne pas le désactiver.
- Aucune valeur spécifique à un provider en dur dans le code.

## Critères d'acceptation

- `GET /api/auth/oidc/login` redirige vers le provider avec `state` +
  `code_challenge` et pose `oidc_tx` ;
- `redirectTo` non sûr → repli sur le défaut ;
- callback avec `state` invalide ou sans cookie → `401` `OIDC_STATE_INVALID` ;
- callback nominal (`OidcService` mocké) → user lié/créé, cookies
  refresh/csrf posés, 302 vers le front avec le token en fragment ;
- `provider` renvoie `enabled:false` quand OIDC non configuré ;
- tests d'intégration `OidcController` + unitaires `OidcUserLinker` /
  `resolve-oidc-config` / `sanitize-relative-path` / `extractRoles` ;
  (l'e2e complet contre un faux issuer réseau est repoussé — test manuel
  contre un Keycloak réel) ;
- `nx run-many -t lint,test,build` OK.

## Résumé d'implémentation

**Écarts assumés vs plan initial** : (1) `openid-client` **v5** (CJS) et
non v6 (ESM pur, incompatible avec le backend NestJS CommonJS) ; (2) pas
de flag `--oidc` — OIDC livré avec le brick, activé par la config
(cohérent step 21) ; (3) **lien par email vérifié**, pas de champ
`oidcSub` sur le schéma `user` (évite qu'un generator patche une autre
lib ; l'`id_token.email` + `email_verified` est autoritaire) ;
(4) `OIDC_FRONTEND_URL` au lieu de `FRONTEND_URL` (groupé sous
`config.oidc`, pas de casse des specs `config`) ; (5) test d'intégration
`OidcController` (service mocké) au lieu d'un faux serveur OIDC réseau.
`V2.md` mis à jour (steps 22 et 29).
