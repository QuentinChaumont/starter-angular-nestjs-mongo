# Starter Nx Angular + NestJS + Mongo — V2

## Objectif

La V1 a produit un socle backend complet et un ensemble de briques
optionnelles côté serveur (Mongo, CRUD, Auth JWT, Authorization, Security,
Health). Le frontend, lui, est resté un squelette (`app.routes.ts` vide,
`styles.scss` vide, `libs/frontend/core` sans contenu).

La V2 construit progressivement la **couche frontend du starter**, sur le
même principe que la V1 : des briques opt-in installées par des generators
Nx locaux, jamais imposées au runtime.

Briques ajoutées :

- **auth avancé backend** : refresh tokens + rotation + logout ;
- **login OIDC backend** : Authorization Code + PKCE, find-or-create user,
  émission du JWT maison ;
- **`frontend-design`** : Angular Material + CDK, thème Material 3
  (light/dark), charte graphique versionnée (`design.config.ts`) et
  `DESIGN.md` propre au projet ;
- **couleurs paramétrables** : hybride build-time (charte par défaut) +
  runtime (CSS custom properties, `ThemeService`, panneau de réglages UI,
  persistance `localStorage`) ;
- **`frontend-auth`** : écran de login, store d'auth (signals),
  intercepteur HTTP (bearer + `X-Request-Id` + refresh-on-401), guards de
  route, bouton de connexion OIDC ;
- **`frontend-dashboard`** : shell applicatif `MatSidenav` responsive
  devenant le layout par défaut des routes protégées ;
- **`frontend-feedback`** : gestion centralisée des popups (`DialogService`)
  et des notifications/toasts (`NotificationService`), branchées sur le
  format d'erreur `ApiError` de la V1 ;
- **`frontend-consent`** : popup légale de consentement (cookies / traceurs)
  affichée à l'arrivée sur le site, avec catégories, persistance du choix,
  re-consultation, et pages légales générées.

Le starter doit rester **modulaire** : un projet qui n'a besoin ni de
frontend riche, ni d'auth, ni de dashboard doit pouvoir ignorer toutes ces
briques et garder le socle V1 intact.

---

## Décisions d'architecture V2 (déjà tranchées)

Ces choix s'appliquent à toutes les étapes ci-dessous. Ne pas les
réinterroger pendant l'implémentation.

### Transport du refresh token — cookie httpOnly

- L'**access token** (JWT court, ~15 min) est renvoyé dans le corps de la
  réponse et gardé **en mémoire** côté Angular (jamais `localStorage`).
- Le **refresh token** est posé dans un cookie `httpOnly` + `Secure` +
  `SameSite=Lax`, scope path `/api/auth`. Le SPA n'y a jamais accès en JS.
- `POST /api/auth/refresh` lit le cookie, effectue la **rotation** (ancien
  token révoqué, nouveau émis), renvoie un nouvel access token.
- Protection CSRF de `/api/auth/refresh` et `/api/auth/logout` :
  **double-submit token**. À l'émission d'une session, le serveur pose
  aussi un cookie `csrf-token` **non-httpOnly** ; le SPA le recopie dans
  l'en-tête `X-CSRF-Token` sur ces deux routes ; le serveur compare.
- Impacts : CORS avec `credentials: true` (déjà géré par la brique
  Security, `CORS_ORIGINS`), et un `AuthCookieService` côté backend
  centralisant la pose/suppression des cookies.

### Packaging OIDC — option du brick auth (`--oidc`)

- Un seul brick auth backend et un seul brick `frontend-auth`.
- Le generator backend `auth` gagne deux flags : `--refresh` (V2, activé
  par défaut) et `--oidc` (opt-in).
- Le login **local** (email + mot de passe, V1) et le login **OIDC**
  coexistent : en dev on peut travailler sans IdP.
- OIDC est un **fournisseur d'identité en amont** : après le callback, le
  starter crée/retrouve le `user` local et émet **son propre** JWT. Le
  token du provider OIDC n'est jamais renvoyé au client ni stocké.

### Couleurs paramétrables — hybride build + runtime

- `libs/frontend/design/src/lib/theme/design.config.ts` : source de vérité
  **versionnée** de la charte (couleurs de marque, rayons, densité,
  typo). Consommée au build pour générer les valeurs par défaut des CSS
  custom properties et le thème Material.
- Runtime : toutes les couleurs clés sont exposées en CSS custom
  properties (`--app-color-primary`, `--app-color-surface`, …) sur
  `:root`. Un `ThemeService` permet de les surcharger, de basculer
  light/dark, et persiste le choix dans `localStorage`
  (`app.theme.*`), avec `try/catch` et repli sur la charte par défaut.
- Un composant `ThemeSettingsPanel` (dans la brique design) fournit l'UI
  de personnalisation ; le dashboard l'expose depuis son menu utilisateur.

### `frontend-dashboard` — shell par défaut

- Le generator réécrit `apps/frontend/src/app/app.ts` et `app.routes.ts` :
  - routes publiques (`/login`, `/auth/callback`) hors shell ;
  - routes applicatives regroupées sous `/app` derrière `authGuard`, à
    l'intérieur du `DashboardShellComponent` (toolbar + sidenav +
    `<router-outlet>`).
- Le menu latéral est **config-driven** (`DASHBOARD_NAV` : liste
  d'entrées `{ label, icon, route, roles? }`).
- Idempotent : relancer le generator ne duplique ni le shell ni les routes.

Reprennent ceux de la V1, avec ces précisions frontend.

```text
apps/

└── frontend/          app.ts / app.config.ts / app.routes.ts =
                       composition root uniquement

libs/
├── backend/
│   ├── core/
│   ├── database/mongo/
│   ├── auth/          + refresh tokens, + stratégie OIDC (opt-in)
│   ├── testing/
│   └── features/
│
├── frontend/
│   ├── core/          toujours présent : tokens d'environnement,
│   │                  HttpClient de base, helpers RxJS/signals
│   ├── design/        (brique) Material + CDK + thème + charte
│   ├── auth/          (brique) login, store, interceptor, guards
│   ├── dashboard/     (brique) shell applicatif
│   ├── feedback/      (brique) popups + notifications
│   └── consent/       (brique) consentement cookies + pages légales
│
└── shared/

    └── utils/
```

### Règles de développement (ajouts V2)

- Pas de librairie de state management externe (NgRx, etc.) : signals +
  services.
- Pas de framework de composants tiers autre qu'Angular Material / CDK.
- `libs/frontend/core` ne dépend **pas** de `@angular/material` : tout ce
  qui touche Material vit dans `frontend/design` ou au-dessus.
- Les composants consomment les **CSS custom properties**, jamais une
  couleur en dur ni un `$sass-var` de couleur de marque.
- `shared/contracts` reste sans dépendance Angular / Nest / Mongoose /
  Passport / openid-client.
- Le SPA ne stocke jamais de token en `localStorage` (access en mémoire,
  refresh en cookie httpOnly).
- Chaque brique frontend est installable indépendamment, avec un message
  d'erreur actionnable si un prérequis manque (comme les briques V1).
- Chaque étape doit compiler, `lint` + `test` + `build` doivent passer.
- Ne jamais développer une étape suivante par anticipation.

### Workflow attendu pour chaque step

Identique à la V1 :

1. analyser le code existant ;
2. proposer brièvement les fichiers créés / modifiés ;
3. implémenter uniquement le périmètre de l'étape ;
4. lancer `lint` / `test` / `build` pertinents (via `nx`) ;
5. corriger les erreurs ;
6. résumer les modifications dans le step ;
7. ajouter le coût en tokens de l'étape en fin de résumé ;
8. s'arrêter.

# STEP 21 — Auth avancé : refresh tokens, rotation, logout

## Objectif

Étendre `libs/backend/auth` (V1) avec une vraie gestion de session :
refresh token en cookie httpOnly, rotation, révocation, logout.

## Emplacement

```text
libs/backend/auth/src/lib/
├── refresh/
│   ├── refresh-token.schema.ts      // Mongo : userId, tokenHash, family, expiresAt, revokedAt, replacedBy, userAgent, ip
│   ├── refresh-token.repository.ts  // via BaseRepository<T>
│   └── refresh-token.service.ts     // issue / rotate / revoke / revokeAllForUser
├── cookies/
│   └── auth-cookie.service.ts       // pose/suppression cookies refresh + csrf
├── csrf/
│   └── csrf.guard.ts                // double-submit : compare cookie csrf-token et header X-CSRF-Token
└── auth.controller.ts               // + refresh / logout
```

## Dépendances

```text
cookie-parser        // + @types/cookie-parser
```

(`@nestjs/jwt`, `passport-jwt` déjà là depuis la V1.)

## Fonctionnalités

- `POST /api/auth/login` (existant) : en plus du corps
  `AccessTokenResponse`, pose le cookie `refresh_token` (httpOnly, Secure,
  SameSite=Lax, path `/api/auth`) **et** le cookie `csrf-token`
  (non-httpOnly, même durée que le refresh).
- `POST /api/auth/refresh` :
  - protégé par `CsrfGuard` ;
  - lit le cookie, vérifie hash + expiration + non-révocation ;
  - **rotation** : révoque l'ancien (`revokedAt`, `replacedBy`), émet un
    nouveau refresh (même `family`), renvoie un nouvel access token ;
  - **détection de réutilisation** : si un token déjà révoqué est
    présenté, révoquer toute la `family` et répondre `401`.
- `POST /api/auth/logout` : protégé par `CsrfGuard`, révoque le refresh
  courant, efface les deux cookies.
- Refresh token : valeur aléatoire (`crypto.randomBytes`), stockée
  **hashée** (SHA-256) en base — jamais en clair.
- Durées via config : `JWT_EXPIRES_IN` (access, défaut `15m`),
  `REFRESH_EXPIRES_IN` (défaut `30d`).
- `RefreshTokenService.revokeAllForUser(userId)` exposé pour un futur
  « déconnecter partout ».
- Nettoyage : les tokens expirés depuis longtemps peuvent être purgés à la
  volée lors de la rotation (pas de cron en V2).

## Generator

`tools/starter-plugin/src/generators/auth` :

- nouveau flag `--refresh` (défaut `true`) ;
- idempotent : ne ré-ajoute pas `cookie-parser` ni la config si présents ;
- ajoute `app.use(cookieParser())` dans `main.ts` via un helper
  `_shared` (nouvel `ensure-line-after-anchor` ou équivalent).

## Config

Nouvelle variable :

| Variable | Requis | Défaut | Notes |
| --- | --- | --- | --- |
| `REFRESH_EXPIRES_IN` | non | `30d` | Lu seulement si auth installée |
| `AUTH_COOKIE_SECURE` | non | `true` en prod, `false` sinon | Permet le dev en http |

## Critères d'acceptation

- login pose les cookies attendus ;
- `refresh` sans cookie → `401` ; avec cookie valide → nouvel access
  token + nouveau cookie refresh (valeur différente) ;
- rejouer un refresh déjà tourné → `401` + famille révoquée ;
- `refresh` / `logout` sans `X-CSRF-Token` correct → `403` ;
- `logout` efface les cookies et révoque le token ;
- format d'erreur V1 respecté, `requestId` présent ;
- tests E2E : login → refresh → refresh (rotation) → reuse → logout ;
- tests unitaires `RefreshTokenService` et `CsrfGuard` ;
- `nx run-many -t lint,test,build` OK ;
- relancer le generator ne casse rien.

# STEP 22 — Login OIDC (Authorization Code + PKCE)

## Objectif

Permettre la connexion via un fournisseur OIDC générique (Keycloak,
Google, Azure AD…), en gardant l'émission du JWT maison.

## Emplacement

```text
libs/backend/auth/src/lib/oidc/
├── oidc.config.ts       // lecture config, no-op si non configuré
├── oidc.service.ts      // openid-client : discovery, authURL + PKCE, callback exchange
├── oidc.controller.ts   // GET /api/auth/oidc/login, GET /api/auth/oidc/callback
└── oidc-user.linker.ts  // find-or-create user local à partir des claims
```

## Dépendances

```text
openid-client
```

Pas de Passport pour OIDC (on reste découplé, cf. principe V1).

## Fonctionnalités

- `GET /api/auth/oidc/login?redirectTo=/app/...` :
  - génère `state` + `code_verifier` (PKCE), les stocke dans un cookie
    court signé / httpOnly (`oidc_tx`, ~10 min) ;
  - redirige (302) vers l'`authorization_endpoint` du provider.
- `GET /api/auth/oidc/callback?code&state` :
  - vérifie `state` contre le cookie `oidc_tx` ;
  - échange le `code` (+ `code_verifier`) contre les tokens du provider ;
  - valide l'`id_token`, extrait `sub`, `email`, (`name`, `roles` si
    présents) ;
  - `OidcUserLinker` : retrouve le `user` par `oidcSub` puis par `email`,
    sinon le crée (sans mot de passe) ; met à jour `oidcSub` ;
  - émet l'access token + pose les cookies refresh/csrf (réutilise le
    `RefreshTokenService` du step 21) ;
  - redirige vers `FRONTEND_URL + redirectTo` (validé : chemin relatif
    uniquement) avec l'access token passé en fragment `#access_token=...`
    **ou** via une page intermédiaire — choix : fragment, consommé puis
    nettoyé par le front (step 25).
- `GET /api/auth/oidc/provider` → `OidcProviderInfo` (`enabled`,
  `loginUrl`) pour que le front affiche ou non le bouton.
- Schéma `user` : champ optionnel `oidcSub?: string` (indexé, sparse
  unique). Le generator `entity user` V1 n'est pas modifié ; le brick auth
  `--oidc` applique une petite migration de schéma additive.

## Generator

`auth` : nouveau flag `--oidc` (défaut `false`). Installe `openid-client`,
ajoute `OidcModule`, documente les variables. Idempotent.

## Config

| Variable | Requis | Défaut | Notes |
| --- | --- | --- | --- |
| `OIDC_ISSUER` | si `--oidc` | — | URL de discovery |
| `OIDC_CLIENT_ID` | si `--oidc` | — | |
| `OIDC_CLIENT_SECRET` | non | — | Vide pour un client public + PKCE |
| `OIDC_REDIRECT_URI` | si `--oidc` | — | `.../api/auth/oidc/callback` |
| `OIDC_SCOPES` | non | `openid profile email` | |
| `OIDC_POST_LOGIN_REDIRECT` | non | `/app` | Chemin relatif front |
| `FRONTEND_URL` | si `--oidc` | `http://localhost:4200` | Base des redirections |

Toutes ignorées si `--oidc` non installé.

## Contraintes

- Le token du provider OIDC ne sort jamais du backend.
- `redirectTo` : rejeter toute valeur absolue ou commençant par `//`.
- Fonctionne à côté du login local — ne pas le désactiver.
- Aucune valeur spécifique à un provider en dur dans le code.

## Critères d'acceptation

- `GET /api/auth/oidc/login` redirige vers le provider avec `state` +
  `code_challenge` ;
- callback avec `state` invalide → `401` ;
- callback nominal (provider mocké dans les tests) → user créé/retrouvé,
  cookies posés, redirection front ;
- `provider` renvoie `enabled:false` quand `--oidc` non installé ;
- tests E2E avec un faux serveur OIDC (issuer local) ;
- `nx run-many -t lint,test,build` OK.

# STEP 25 — Brique `frontend-auth`

## Objectif

Connexion côté Angular : login local + OIDC, store d'auth en signals,
intercepteur HTTP, guards de route.

## Emplacement

```text
libs/frontend/auth/
└── src/lib/
    ├── auth.store.ts            // signals : user, status, accessToken (mémoire)
    ├── auth.service.ts          // login, logout, refresh, loadMe, oidcLogin
    ├── auth.interceptor.ts      // Authorization + X-Request-Id + refresh-on-401 (file d'attente)
    ├── auth.guard.ts            // authGuard, roleGuard(...roles)
    ├── csrf.interceptor.ts      // recopie cookie csrf-token -> X-CSRF-Token sur /api/auth/*
    ├── login/                   // LoginPageComponent (form Material + bouton OIDC conditionnel)
    ├── callback/                // OidcCallbackComponent (consomme #access_token, nettoie l'URL)
    └── provide-auth.ts
```

Projet Nx : `frontend-auth`, tags `scope:frontend`, `type:feature`
(dépend de `frontend-design`, `frontend-core`, `shared-contracts`).

## Fonctionnalités

- `AuthStore` : `user: signal<AuthenticatedUserDto | null>`,
  `status: signal<'anonymous' | 'authenticating' | 'authenticated'>`,
  access token **en mémoire uniquement**.
- `AuthService.login(credentials)` → `POST /api/auth/login` (avec
  `withCredentials`), stocke l'access token, `loadMe()`.
- `AuthService.refresh()` → `POST /api/auth/refresh` ; utilisé par
  l'intercepteur sur `401` et au bootstrap (silent refresh) pour
  restaurer une session au reload.
- `authInterceptor` :
  - ajoute `Authorization: Bearer` si token présent ;
  - propage / génère `X-Request-Id` ;
  - sur `401` (hors routes `/api/auth/*`) : tente **un** refresh, met en
    file les requêtes concurrentes, rejoue ; si le refresh échoue →
    `authStore.reset()` + redirection `/login`.
- `csrfInterceptor` : lit le cookie `csrf-token` (non-httpOnly), ajoute
  `X-CSRF-Token` sur `refresh` / `logout`.
- `authGuard` : redirige vers `/login?redirectTo=...` si non authentifié
  (tente d'abord un silent refresh). `roleGuard('admin')` : `403` → page
  ou redirection.
- `LoginPageComponent` : formulaire réactif Material ; affiche le bouton
  « Se connecter avec OIDC » seulement si `GET /api/auth/oidc/provider`
  renvoie `enabled:true`.
- `OidcCallbackComponent` : lit `#access_token` du fragment, le stocke,
  nettoie l'URL (`history.replaceState`), `loadMe()`, redirige vers
  `redirectTo`.
- `provideAuth()` : enregistre les intercepteurs + déclenche le silent
  refresh initial.

## Generator

`tools/starter-plugin/src/generators/frontend-auth` :

- prérequis vérifiés avec message actionnable : brique `frontend-design`
  installée, et backend auth (`libs/backend/auth`) présent ;
- copie la lib, ajoute `provideAuth()` dans `app.config.ts` ;
- ajoute les routes `/login` et `/auth/callback` dans `app.routes.ts` ;
- idempotent.

## Contraintes

- Aucun token en `localStorage`.
- Un seul refresh en vol à la fois (mutex / `shareReplay`).
- L'intercepteur ne doit pas boucler sur `/api/auth/refresh`.
- `frontend-auth` ne connaît pas la brique dashboard (les routes
  protégées sont câblées par le dashboard au step 26, ou à la main).

## Critères d'acceptation

- login local → session active, `user` peuplé ;
- reload → session restaurée via silent refresh ;
- access token expiré → `401` intercepté, refresh transparent, requête
  rejouée ;
- refresh échoué → retour `/login` propre ;
- bouton OIDC visible seulement si le provider est activé ; flux callback
  fonctionnel (backend OIDC mocké) ;
- `authGuard` / `roleGuard` testés ;
- `nx run-many -t lint,test,build` OK ;
- relancer le generator ne duplique ni routes ni providers.

# STEP 28 — Brique `frontend-consent` : popup légale cookies / traceurs

## Objectif

Afficher, à la première arrivée sur le site, une popup légale de
consentement (cookies, traceurs, mesure d'audience, etc.), conforme à
l'esprit RGPD / ePrivacy : rien de non essentiel n'est activé tant que
l'utilisateur n'a pas choisi, le choix est mémorisé, et il reste
révocable à tout moment.

## Emplacement

```text
libs/frontend/consent/
└── src/lib/
    ├── consent.config.ts          // catégories, version de politique, liens légaux, durée
    ├── consent.types.ts           // ConsentCategory, ConsentDecision, ConsentState
    ├── consent.service.ts         // signals : state, hasDecided ; accept/reject/save/reset
    ├── consent.storage.ts         // persistance localStorage + expiration + version
    ├── consent-gate.ts            // runWhenConsented(category, fn) / *consentIf directive
    ├── banner/
    │   └── consent-banner.component.ts     // bandeau : Tout accepter / Tout refuser / Personnaliser
    ├── preferences/
    │   └── consent-preferences.component.ts // dialog : toggle par catégorie + enregistrer
    ├── legal/
    │   ├── cookie-policy.page.ts           // templates générés (à compléter par projet)
    │   └── privacy-policy.page.ts
    └── provide-consent.ts
```

Projet Nx : `frontend-consent`, tags `scope:frontend`, `type:util`
(dépend de `frontend-design` ; utilise `frontend-feedback` pour le dialog
de préférences si présent, sinon fournit son propre overlay CDK).

## Fonctionnalités

- `consent.config.ts` : liste des catégories, typée. Toujours au moins :
  - `essential` — non désactivable, coché et verrouillé ;
  - catégories opt-in configurables (`analytics`, `marketing`, …) avec
    `label`, `description`.
  - `policyVersion` (string) et `expiresInDays` (défaut `182` ≈ 6 mois).
  - `legal` : URLs / routes des mentions légales et de la politique cookies.
- `ConsentService` :
  - `state: signal<ConsentState>` , `hasDecided: computed` ;
  - `acceptAll()`, `rejectAll()`, `save(decision: Record<category, boolean>)` ;
  - `reopen()` — ré-affiche la popup / le dialog de préférences ;
  - `isGranted(category): Signal<boolean>` ;
  - persistance `localStorage` (`app.consent`) via `consent.storage.ts`,
    avec `try/catch` et repli « non décidé » ;
  - **re-consentement** automatique si le choix est expiré **ou** si
    `policyVersion` a changé depuis le choix enregistré.
- `ConsentBannerComponent` :
  - s'affiche uniquement si `!hasDecided()` ;
  - **non bloquant** pour le premier rendu (n'empêche pas le paint, mais
    reste visible et au-dessus du contenu — `role="dialog"`,
    `aria-live`, focus trap CDK) ;
  - actions : « Tout accepter », « Tout refuser », « Personnaliser »
    (ouvre `ConsentPreferencesComponent`) ;
  - lien vers la politique cookies.
- `ConsentPreferencesComponent` : un toggle par catégorie (essential
  verrouillé), bouton « Enregistrer mes choix ».
- `consent-gate` : `runWhenConsented('analytics', () => loadTag())` et une
  directive structurelle `*consentIf="'marketing'"` pour ne rendre un bloc
  (ex. iframe tierce) qu'après consentement. Aucun script tiers n'est
  chargé par le starter lui-même — le gate est le point d'accroche.
- `provideConsent(config?)` : fournit la config, initialise le service au
  bootstrap (lecture du choix persisté avant premier rendu utile).
- Pages légales (`cookie-policy`, `privacy-policy`) : **templates**
  générés, jamais écrasés ; contiennent des placeholders explicites
  (raison sociale, DPO, finalités, durées) à compléter par le projet.

## Generator

`tools/starter-plugin/src/generators/frontend-consent` :

- prérequis : `frontend-design` installé (message actionnable sinon) ;
- copie la lib, ajoute `provideConsent()` dans `app.config.ts` ;
- monte `<app-consent-banner />` **hors** du shell dashboard (dans
  `app.ts`, au-dessus du `<router-outlet>`, pour couvrir pages publiques

- génère les pages légales si absentes ;
- idempotent.

## Contraintes

- Le bandeau ne doit **pas** retarder le premier rendu ni bloquer la
  navigation ; il informe et propose, il ne verrouille pas l'écran.
- « Refuser » doit être aussi accessible qu'« Accepter » (même niveau
  visuel — pas de dark pattern).
- Aucun cookie / traceur non essentiel posé avant décision : le starter
  ne fournit aucun tag analytics, seulement le mécanisme de gate.
- Le choix « refuser » est un choix : `hasDecided` devient vrai, le

- Textes en dur → même point d'extension i18n futur que le step 27 (ne
  pas l'implémenter).
- `frontend-consent` ne doit pas dépendre de `frontend-auth` ni de

## Critères d'acceptation

- première visite → bandeau visible, contenu accessible derrière ;
- « Tout accepter » / « Tout refuser » → bandeau disparaît, choix

# Résultat attendu de la V2

Le socle V1 reste intact et minimal. Un projet peut désormais, en plus,
activer une **couche frontend cohérente** :

```text
frontend-design     Material + CDK + charte + thème light/dark

frontend-dashboard  shell sidenav responsive = layout par défaut de /app
```

Le principe V1 est conservé :

> Le starter fournit les conventions et les generators. Il n'impose au
> runtime aucune fonctionnalité — front comprise — dont le projet n'a pas
> besoin.
