# Starter Nx Angular + NestJS + Mongo — V1

## Objectif

Construire progressivement un starter Nx réutilisable contenant :

- une application Angular ;
- une application NestJS ;
- un socle backend commun ;
- un logger sans dépendance externe ;
- une configuration typée et validée ;
- une gestion homogène des erreurs ;
- une validation globale des entrées ;
- des contrats partagés front/back ;
- Swagger / OpenAPI ;
- une intégration MongoDB via Mongoose ;
- une couche Repository légère ;
- un système de generators Nx locaux ;
- un generator d'entity CRUD ;
- une authentification JWT via Passport ;
- les briques de sécurité HTTP essentielles ;
- des healthchecks adaptés à un déploiement conteneurisé / Kubernetes.

Le starter doit rester **modulaire** : MongoDB, CRUD, Auth, Security et Health doivent pouvoir être ajoutés uniquement lorsqu'un projet en a besoin.

---

# Principes généraux à respecter

Ces règles s'appliquent à toutes les étapes.

## Architecture

Conserver une séparation claire entre :

```text
apps/
├── api/
└── web/

libs/
├── backend/
│   ├── core/
│   ├── database/
│   ├── auth/
│   └── features/
│
├── frontend/
│   ├── core/
│   ├── auth/
│   ├── data-access/
│   └── features/
│
└── shared/
    ├── contracts/
    └── utils/

tools/
└── starter-plugin/
```

Adapter les noms aux conventions Nx déjà présentes dans le workspace si nécessaire.

## Règles de développement

- Ne pas ajouter de dépendance sans nécessité.
- Ne pas introduire de framework CRUD runtime générique.
- Ne pas générer de logique métier implicite.
- Préférer du code explicite et simple.
- Respecter les boundaries Nx entre libs.
- Éviter les imports directs entre features.
- Centraliser les éléments transverses dans `backend/core`.
- Les repositories ne doivent dépendre que de la couche database et de leur feature.
- Les controllers ne doivent pas accéder directement à Mongoose.
- Les services métier ne doivent pas manipuler directement les modèles Mongoose.
- Aucun code Firebase.
- L'authentification doit rester découplée de Passport autant que possible.
- Chaque étape doit compiler et fonctionner avant de passer à la suivante.
- Ajouter ou adapter les tests pertinents à chaque étape.
- Ne jamais développer une étape suivante par anticipation.

## Workflow attendu pour chaque step

Pour chaque étape :

1. analyser le code existant ;
2. proposer brièvement les fichiers qui seront créés ou modifiés ;
3. implémenter uniquement le périmètre de l'étape ;
4. lancer les tests/lint/build pertinents ;
5. corriger les erreurs ;
6. résumer les modifications ici dans chaque step;
7. Ajouter le cout en token pour l'ensemble de cette étape en fin de resumé
8. s'arrêter.

# STEP 1 — Normaliser la structure Nx

## Objectif

Créer la structure minimale des libs qui serviront de socle au starter.

## À créer

```text
libs/
├── backend/
│   └── core/
├── frontend/
│   └── core/
└── shared/
    ├── contracts/
    └── utils/
```

Créer uniquement les projets Nx nécessaires.

Ne pas ajouter Mongo, Passport ou autre dépendance fonctionnelle à cette étape.

## Contraintes

- Utiliser les generators Nx officiels.
- Utiliser des tags Nx permettant ensuite de définir les boundaries.

Exemple de tags possibles :

```text
scope:backend
scope:frontend
scope:shared

type:core
type:feature
type:data-access
type:contracts
type:util
```

Configurer les règles de dépendances Nx si elles ne sont pas déjà présentes.

## Critères d'acceptation

- `nx graph` fonctionne.
- Angular compile.
- NestJS compile.
- Les libs créées sont importables.
- Les boundaries empêchent au minimum une lib frontend de dépendre directement d'une lib backend.
- Aucun comportement applicatif n'a été ajouté.

# STEP 3 — Logger applicatif sans librairie externe

## Objectif

Créer un logger standardisé utilisant uniquement les capacités natives de NestJS et Node.

## Emplacement

```text
libs/backend/core/logger
```

## Fonctionnalités

Créer un logger basé sur :

```ts
ConsoleLogger
```

Le logger doit permettre :

```ts
logger.log(...)
logger.debug(...)
logger.warn(...)
logger.error(...)
```

Les logs doivent pouvoir être structurés.

Ajouter un contexte de requête utilisant :

```ts
AsyncLocalStorage
```

Chaque requête HTTP doit disposer d'un :

```text
requestId
```

Le `requestId` doit :

- être récupéré depuis un header entrant s'il est présent et acceptable ;
- sinon être généré via `crypto.randomUUID()`;
- être accessible automatiquement depuis le logger ;
- être retourné dans un header HTTP de réponse.

Exemple de log :

```json
{
  "level": "error",
  "message": "Unable to update user",
  "context": "UserService",
  "requestId": "..."
}
```

## Contraintes

Ne pas installer :

```text
winston
pino
nestjs-pino
```

## Critères d'acceptation

- chaque requête possède un `requestId` ;
- le même `requestId` est accessible dans controller/service/repository ;
- les logs incluent automatiquement ce contexte ;
- aucune dépendance de logging externe ;
- tests du request context ;
- tests du logger.

# STEP 4 — Gestion globale des erreurs HTTP

## Objectif

Uniformiser les erreurs retournées par l'API.

## Emplacement

```text
libs/backend/core/http
```

## À créer

```text
errors/
filters/
interceptors/
```

Créer une erreur applicative de base.

Exemple :

```ts
ApplicationError
```

Puis quelques erreurs spécialisées :

```ts
NotFoundError
ConflictError
ForbiddenError
UnauthorizedError
ValidationError
```

Créer un `GlobalExceptionFilter`.

## Format de réponse attendu

```json
{
  "statusCode": 404,
  "code": "USER_NOT_FOUND",
  "message": "User not found",
  "requestId": "..."
}
```

En développement, il est possible d'ajouter davantage de détails.

En production, ne jamais exposer :

- stack trace ;
- exception Mongo brute ;
- informations internes ;
- secrets.

## Critères d'acceptation

- format d'erreur identique pour toute l'API ;
- `requestId` présent ;
- mapping correct des erreurs applicatives ;
- erreurs inconnues transformées en HTTP 500 ;
- erreur originale loggée côté serveur ;
- aucune stack exposée en production ;
- tests unitaires du filter.

## Critères d'acceptation

- validation activée globalement ;
- propriétés inconnues refusées ;
- transformation des paramètres lorsque nécessaire ;
- format d'erreur homogène ;
- tests E2E d'au moins un endpoint invalide.

# STEP 11 — Generator `entity`

## Objectif

Créer le principal generator du starter pour les entities Mongo.

## Commande cible

Par exemple :

```bash
nx g @starter/entity user
```

Options possibles :

```bash
nx g @starter/entity user --crud
```

Prévoir dès la conception la possibilité future de :

```text
--frontend
--no-controller
--no-repository
```

mais ne pas nécessairement toutes les implémenter en V1.

## Sans `--crud`

Générer :

```text
libs/backend/features/user/
└── src/lib/
    ├── user.module.ts
    ├── user.service.ts
    ├── user.repository.ts
    ├── user.schema.ts
    └── models/
```

## Avec `--crud`

Ajouter :

```text
user.controller.ts

dto/
├── create-user.dto.ts
└── update-user.dto.ts
```

Routes attendues :

```text
POST   /users
GET    /users
GET    /users/:id
PATCH  /users/:id
DELETE /users/:id
```

## Règles

Le controller appelle le service.

Le service appelle le repository.

Le repository appelle Mongoose.

Donc :

```text
Controller
   ↓
Service
   ↓
Repository
   ↓
Mongoose
```

Ne jamais générer :

```text
Controller → Model
```

ou :

```text
Service → InjectModel
```

## Critères d'acceptation

La commande :

```bash
nx g @starter/entity user --crud
```

doit produire une feature compilable immédiatement.

Le CRUD généré doit fonctionner après déclaration de quelques propriétés dans le schema/DTO.

Ajouter les tests du generator.

# STEP 13 — Authentification JWT optionnelle

## Objectif

Ajouter une authentification backend réutilisable.

## Emplacement

```text
libs/backend/auth
```

## Dépendances

Utiliser :

```text
@nestjs/passport
passport
passport-jwt
@nestjs/jwt
```

Aucun Firebase.

## Architecture cible

```text
libs/backend/auth/
├── auth.module.ts
├── auth.service.ts
├── guards/
├── strategies/
├── decorators/
└── models/
```

Créer notamment :

```text
JwtStrategy
JwtAuthGuard
CurrentUser decorator
```

## Modèle exposé au domaine

Éviter de propager directement les types Passport.

Définir par exemple :

```ts
export interface AuthenticatedUser {
  id: string;
  roles: string[];
}
```

Le reste du code doit dépendre de ce type plutôt que de Passport.

## Configuration

Utiliser :

```text
JWT_SECRET
JWT_EXPIRES_IN
```

via la lib config.

La présence de ces variables ne doit être obligatoire que lorsque l'auth est activée.

## Endpoints V1

Créer au minimum un mécanisme permettant de tester :

```text
POST /auth/login
GET /auth/me
```

Pour le starter, le login peut s'appuyer sur l'entity `User` de démonstration.

Ne pas implémenter OAuth/OIDC dans cette version.

## Critères d'acceptation

- login retourne un JWT ;
- route protégée inaccessible sans token ;
- token valide accepté ;
- token invalide/refusé proprement ;
- `CurrentUser` fonctionne ;
- tests E2E auth.

# STEP 16 — Healthchecks optionnels

## Objectif

Préparer le backend aux environnements Docker / Kubernetes.

## Dépendance

Utiliser :

```text

```

## Endpoints

Créer :

```text

```

### Liveness

Doit uniquement vérifier que le processus NestJS fonctionne.

### Readiness

Doit vérifier les dépendances nécessaires, notamment Mongo si Mongo est activé.

## Critères d'acceptation

```text
Angular
NestJS
Config
Logger
Request Context
Global Errors
Validation
Contracts
OpenAPI
```

Puis d'activer uniquement les briques nécessaires :

```text

```

Le principe central est :

> Le starter fournit les conventions et les generators. Il ne doit pas imposer au runtime des fonctionnalités dont le projet n'a pas besoin.
